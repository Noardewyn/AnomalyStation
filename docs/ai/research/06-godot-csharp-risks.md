# 06. Risks of the Godot 4 + C# Stack for a Large Multiplayer Simulation

Research date: 2026-10-05. Planned stack: Godot 4.7.2 (mono) + C# / .NET 10, the simulation Kernel as a separate C# library with no dependency on Godot, Godot as the client.
Confidence: high = a fact from a primary source that I opened or measured; medium = a secondary source, a user post, or my own inference; low = a search snippet, outdated data, or a hypothesis.

## Summary

1. ⚠️ The built-in High-level multiplayer API with ENet is risky to use as the basis of a server for 100–250 players. The only public test of a similar scale that I found (CipSoft, Godot 4.4.1 + C#, server with 2 cores / 2 GB) hit mass disconnects at 80–100 clients and replaced the networking with its own. But the CipSoft post did not analyze the cause, and an independent analysis of the same kind of failure (F2) points to default settings (`server_relay`, vsync, a single channel) and, after changing them, reaches hundreds to thousands of connections in a synthetic test. The claim "not suitable" is proven only for the default configuration on weak hardware. Additionally, there is a public issue about an overflow in spawn replication (#121640, July 2026): ⚠️ not confirmed by maintainers (label `needs testing`), open, no fix.
2. I did not find a single shipped 3D game on Godot with 100+ players on one server (negative result, search limit exhausted, not rechecked). The examples found are either 2D, or Godot serves only as the client while the server is written separately (Go and Elixir confirmed for Cozy Quest; ⚠️ "Rust, C++" is not confirmed in the report's sources). SS14 used Godot 3 as the client layer for rendering/audio/input/GUI (2018) and abandoned Godot altogether in 2019, so "the same pattern" holds only for the client/server split, not for the outcome.
3. The architecture that follows from what was found: authoritative server = a pure .NET process on the Kernel, a custom protocol over a UDP library, chunk-based interest management, Godot = client (rendering, input, UI, audio). This matches your plan of "the Kernel as a separate library". I verified locally that such a structure builds and runs on Godot 4.7.2 with net10.0.
4. Main client risks: lighting (on the tg maps 641 (Meta) and 757 (Delta) light fixtures `/obj/machinery/light/*` (the first version of the report said 770/890, which mistakenly included light switches); the limit of 512 clustered elements and 88 shadows in the atlas apply per frame/camera, not to the whole map, so the entire station will not end up in the frame, but dense compartments and long view distances may hit it), the cost of a scene with tens of thousands of nodes (`RenderingServer`/MultiMesh per chunk are needed), the static nature of baked light with a destructible station.
5. C# in Godot is acceptable on desktop, but it is second-tier: no web, mobile platforms are experimental, no C# profiler in the editor, 528 open C# issues, hot reload loses state. Interop is cheap (about 50–90 ns per call by my measurements, see F11), but strings and Variant collections create garbage.
6. Versions: minor releases every 4–5 months, and patches break things too (a .NET input regression in 4.7.2). Godot 4.8 (feature freeze) raises the minimum TFM to net10.0, while 4.7.x officially targets net8.0. The version must be pinned and upgrades planned in advance.

## Findings

### F1. Versions, TFM, and release cadence (high)
- Godot 4.7.0 was released on 2026-06-18, 4.7.1 on 2026-07-14, 4.7.2 on 2026-08-18: https://godotengine.org/download/archive/4.7.1-stable/ , https://godotengine.org/download/archive/4.7.2-stable/ , https://www.nuget.org/packages/Godot.NET.Sdk/4.7.0
- The GodotSharp 4.7.2 packages on this machine contain only `net8.0` (I unpacked the nupkg from `/Applications/Godot_mono.app`). The 4.7 documentation says: ".NET 8 or newer", for Android .NET 9: https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html
- PR #123738 (merged 2026-09-26) raises the minimum TFM in Godot 4.8 to net10.0 (side effect: Visual Studio 2022 will stop opening projects by default): https://github.com/godotengine/godot/pull/123738 . The 4.8 dev 7 snapshot announced feature freeze: https://godotengine.org/article/dev-snapshot-godot-4-8-dev-7/
- Policy: minor versions roughly every 4 months, only the latest patch is supported, there is no LTS for 4.x, minor upgrades may break small things: https://docs.godotengine.org/en/stable/about/release_policy.html . List of breaking changes 4.6 → 4.7 (Jolt, rendering): https://docs.godotengine.org/en/stable/tutorials/migrating/upgrading_to_godot_4.7.html
- A .NET regression is confirmed in 4.7.2 (raw input, `RIDEV_INPUTSINK`) and assigned to 4.8: https://github.com/godotengine/godot/issues/122716
- Local test (Godot 4.7.2 mono, .NET SDK 10.0.401, arm64 Mac): a project on `Godot.NET.Sdk/4.7.2` with `net10.0` and `LangVersion=14` builds and runs headless on .NET 10.0.12, and `field` from C# 14 compiles. The runtime host (`GodotPlugins.runtimeconfig.json`) is declared as net8.0 with `rollForward: LatestMajor`, so it picks up .NET 10 (`GodotTools.runtimeconfig.json` has `LatestMinor`, but it works inside an already started runtime). I did not check export (no templates) or Android. Rechecked during verification: the test was reproduced, `field` from C# 14 gives the expected result, runtime 10.0.12.
- ⚠️ A caveat on the documentation: when checked, the text of the `stable` page spoke of "Godot 4.5" (.NET 8+, Android .NET 9+), not 4.7; the "4.7 documentation" quote in the first line of this section is inaccurate.

### F2. Scale of the built-in networking (medium-high)
- CipSoft (Tibia) built an MMO tech demo on Godot 4.4.1 C#: client and server from one project, bots from six machines, server on a Linux VM with 2 cores / 2 GB. At 80–100 clients the High-level API with ENet produced CPU spikes and a disconnect of all players. Switching to Telepathy (TCP) with custom wiring improved stability "noticeably" (no figures). The authors' conclusion: the high-level API is insufficient for MMO load: https://forum.godotengine.org/t/our-experience-building-an-mmo-tech-demo-with-godot-4-4-1-net-c/134348 . ⚠️ The post contains no cause analysis and no data on whether they tried disabling `server_relay`/vsync; replies to the post recommend timeout tuning, disabling `SceneTree.MultiplayerPoll`, more powerful hardware, and comparison with LiteNetLib. That is, the conclusion "the API is insufficient" applies to the default configuration on 2 cores.
- Cause analysis (Godot 4.4.1, C# and GDScript): `server_relay` enabled by default, effectively a single working channel, server polling at 60 Hz because of vsync, the channel clogs before the CPU shows load. The author's figures: without RPC broadcast about 4000 connections, one int at 60 Hz about 1500, an array of 75 ints about 430, of 150 ints about 250. Workarounds: disable relay and vsync, explicit `poll()`, increase timeouts, limit the join rate: https://forum.godotengine.org/t/enet-server-drops-all-clients-at-connection-threshold/117785 (a user post, the methodology is reproducible; the figures were checked during verification). A consequence that was not in the first version: these figures were obtained on a synthetic broadcast (whether they refer to before or after the tuning was not unambiguously established during verification); they do not contradict a load of 100–250 clients with a small stream, but the real state stream of an SS13-like simulation is many times larger than an "array of 150 ints", so headroom must not be counted from these figures.
- Documentation: `server_relay=true`, `max_sync_packet_size=1350`, `max_delta_packet_size=65535`; `allow_object_decoding` warns about remote code execution: https://docs.godotengine.org/en/stable/classes/class_scenemultiplayer.html . ENet allows up to 4095 clients, and the practically achievable number "may be much lower".
- Rivet (2023, the 4.1–4.2 era): instability above about 40 CCU, and the absence of prediction and lag compensation is called critical: https://rivet.dev/blog/godot-multiplayer-compared-to-unity/ (outdated, low-medium). The forum claim about an "ENet ceiling of about 32 connections" (https://forum.godotengine.org/t/can-godot-netcode-scale-for-large-multiplayer-scenarios/83561) contradicts the documentation and the tests above (low).

### F3. Security and maturity of the networking module (high / medium)
- Issue #121640 (2026-07-22): an integer overflow in the bounds check of `SceneReplicationInterface::on_spawn_receive()`; according to the author, a specially crafted client spawn packet yields an out-of-bounds read and corruption of the server heap metadata; tested on 4.4.1 and main: https://github.com/godotengine/godot/issues/121640 . Status at verification: the issue is open, labels `bug`, `needs testing`, `topic:multiplayer` (not labeled as security), and there are no maintainer comments, PR, or milestone. ⚠️ So this is an unconfirmed claim by the reporter; "remotely exploitable" in the first version's Summary was stronger than the source. The issue does not mention checking 4.5–4.7.x. As an argument for not exposing `SceneMultiplayer` to untrusted clients it remains reasonable, but it is not decisive on its own.
- 96 `topic:multiplayer` issues and 46 proposals are open (visibility interval, custom marshalling, DTLS for ENet, etc.): https://github.com/godotengine/godot/issues?q=is%3Aissue%20state%3Aopen%20label%3Atopic%3Amultiplayer , https://github.com/godotengine/godot-proposals/issues?q=is%3Aissue%20state%3Aopen%20label%3Atopic%3Amultiplayer . The ENet server closes when an external connection is lost (#115890): https://github.com/godotengine/godot/issues/115890
- Interest management is limited to visibility filters on `MultiplayerSynchronizer` (a callable per peer); there is no spatial index and no prediction; primitives and built-in types are synchronized, not `Resource`: https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html . That a per-peer filter yields O(peers × synchronizers) is my inference (medium).

### F4. Alternative networking solutions (medium)
- LiteNetLib: pure C# UDP, reliable and unreliable channels, MTU auto-detection, .NET 8 and Godot, active development; the README warns that master is unstable: https://github.com/RevenantX/LiteNetLib
- Klotho: a pure C# Kernel, Unity/Godot adapters, the server as a console .NET application on LiteNetLib. The topology is the same as ours, but the project is experimental (62 stars, production use not recommended), the model is deterministic (fixed-point, lockstep/rollback), not an authoritative server: https://github.com/xpTURN/Klotho
- Photon Fusion for Godot: GDExtension, state sync, interest management, prediction, "tens or hundreds" of players claimed; unstable preview (3.0.0-preview-517, July 2026), Godot 4.6–4.7.1: https://store.godotengine.org/asset/photon/photon-fusion/
- GodotSteam (Steam Networking Sockets as a multiplayer peer): the GitHub repository was archived on 2026-09-04, the project moved to Codeberg, C# is not mentioned in the description: https://codeberg.org/godotsteam/godotsteam . EOSG (Epic Online Services for Godot 4.2+): AntiCheat and RTC voice interfaces, works with C#: https://github.com/3ddelano/epic-online-services-godot

### F5. Real examples of scale (medium)
- Survey of games made with Godot in 2026: ⚠️ the first version said "among the hits there is almost no multiplayer, one example". The source lists three multiplayer/co-op games: Soul's Remnant (2D MMORPG, peak 5790 CCU, server architecture unknown to me), Machine Party (2D, 2–4 players, peak 22 629) and Unrailed 2 (co-op, peak 4593, dimensionality and player count not stated in the survey). None of them demonstrates a scale of "100+ on one server"; the best 3D project, Road to Vostok, is single-player: https://godotawesome.com/games-made-with-godot-2026/
- Dome Keeper: online co-op was added in April 2026 to an existing GDScript codebase, the scale is small, and architecture details are not disclosed in the abstract: https://talks.godotengine.org/godotcon-us-2025/talk/XMBFFK/
- Cozy Quest: Godot is only the client (rendering, input, prediction), the backend is in Elixir and Go: https://tappygames.itch.io/cozy-quest/devlog/856145/a-cozy-tour-through-networking-architecture . The game's dimensionality and the number of players per instance are not stated in the devlog. A forum answer: thousands of players are possible, but not in one instance: https://forum.godotengine.org/t/multiplayer-scalability/46309 (⚠️ I did not open this thread during verification, medium → low).
- A reference point from SS14 (not Godot): in the stress test on 9 April 2022, peak about 250 players; 30 TPS held with 200+ players, at 20 TPS at peak it was stable, the bottlenecks were entity spawn/removal and physics (many entities launched into space), plus network hitches at the maximum; the developers estimated the headroom as "250+, possibly up to 350": https://spacestation14.com/post/22-04-30-progress-report-33/ . Their `PvsSystem` divides the world into chunks, cuts by radii and entity budgets, tracks "dirty" ticks, and computes in parallel: https://github.com/space-wizards/RobustToolbox/blob/master/Robust.Server/GameStates/PvsSystem.cs

### F6. Lessons from SS14 with Godot (high for facts, medium for transfer to Godot 4)
- February 2018: a branch on Godot 3 + Mono as the "engine for rendering, sound, input, and GUI", with GLES3 performance problems on macOS: https://spacestation14.com/post/18-02-26-progress-report-5/
- 2019-05-12 ("Bye Godot"): support was removed because of poor UI scaling at 4K, an inflexible renderer (they would have had to build their own renderer on top of someone else's; hence their own Clyde), and localization difficulties (this third argument was missed in the first version): https://spacestation14.com/post/19-05-12-progress-report-15/ . The claims about "constant crashes" and "terrible performance" I saw only in a search snippet (low).
- For content code, SS14 uses IL verification and an API whitelist (`Activator.CreateInstance` and `stackalloc` are blocked): https://docs.spacestation14.com/en/robust-toolbox/sandboxing.html . Godot has no equivalent (F14).

### F8. Rendering large maps and lighting (high)
- Forward+: up to 512 clustered elements (omni, spot, decals, reflection probes) in the camera's field of view, configurable; Mobile: 256 omni + 256 spot per frame and 8+8 per mesh, not configurable; Compatibility: 8+8 per mesh; directional up to 8; the shadow atlas holds 88 shadowed sources by default: https://docs.godotengine.org/en/stable/tutorials/3d/lights_and_shadows.html
- Dynamic light loads the CPU: issue #110436 (growth of "Preparing to render 3D scene", Godot 4.0–4.5, with no maintainer response at the time of checking): https://github.com/godotengine/godot/issues/110436
- GI: LightmapGI is static, with no re-baking at runtime; VoxelGI is dynamic but leaks through thin walls; SDFGI is semi-dynamic; all of this is Forward+ only: https://docs.godotengine.org/en/stable/tutorials/3d/global_illumination/introduction_to_global_illumination.html , https://docs.godotengine.org/en/stable/tutorials/3d/using_lightmap_gi.html . For a destructible station, baked light is almost useless.
- MultiMesh draws thousands of identical objects, but without culling of individual instances, so it must be divided by district: https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html . Occlusion culling rasterizes occluders on the CPU, auto-baking does not account for MultiMesh, and moving occluders are expensive: https://docs.godotengine.org/en/stable/tutorials/3d/occlusion_culling.html . Visibility Ranges (HLOD) exist: https://docs.godotengine.org/en/stable/tutorials/3d/visibility_ranges.html
- The documentation names tens of thousands of instances processed every frame as a scene bottleneck; the way out is the Servers API (`RenderingServer`; RIDs must be freed manually, and references to resources must be kept by yourself): https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html
- Apple Silicon: native Metal (Metal 4 since 4.7), MoltenVK as a fallback; Forward+ and Mobile run on Vulkan, D3D12 (experimental) and Metal: https://docs.godotengine.org/en/stable/engine_details/architecture/internal_rendering_architecture.html

### F9. Physics, Jolt (medium-high)
- Jolt has been the default for new 3D projects since 4.6: https://godotengine.org/releases/4.6/ . Some soft-limit joint properties are not supported, physics in a separate thread is "experimental", and kinematic-vs-static contacts are off by default: https://docs.godotengine.org/en/stable/tutorials/physics/using_jolt_physics.html . In 4.7 the behavior of `SoftBody3D` and `WorldBoundaryShape3D` changed.
- Scene physics is not thread-safe without configuration, while the servers are thread-safe: https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html
- A pure .NET server needs its own physics: BepuPhysics v2 (pure C#, Apache-2.0, 3000+ stars): https://github.com/bepu/bepuphysics2 ; JoltPhysicsSharp (net9.0/net10.0 only): https://github.com/amerkoleci/JoltPhysicsSharp . Divergence between server and client physics must be designed explicitly: either the client only interpolates, or both use the same engine (my inference, medium).

### F10. Navigation and pathfinding (medium)
- `NavigationServer3D` is thread-safe, changes are applied after the next physics frame, and RVO avoidance is expensive with many agents: https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationservers.html . `AStarGrid2D` supports solid cells, weights, and jumping, but `get_point_path()` is not thread-safe: https://docs.godotengine.org/en/stable/classes/class_astargrid2d.html
- Conclusion (medium): for a tile-based station with doors, access, vacuum, and destructible walls, keep the graph and the pathfinding in the C# Kernel and leave `NavigationServer` for client-side cosmetics. The documentation does not describe dynamic chunks and rebaking on tile maps.

### F11. C# performance and GC (medium, local measurements)
One or two runs, Godot 4.7.2 mono, .NET 10.0.12, arm64 Mac, headless, `Optimize=true`:

| Measurement | Result |
|---|---|
| `Node3D.Position` set / get via interop | 78–91 ns / 65–88 ns per call |
| Writing `System.Numerics.Vector3` into an array | 0.7–0.8 ns |
| `Godot.Collections.Array.Add` ×1M versus `List<int>` | 70–84 ms versus 2 ms |
| `Node.Name` get (StringName) | about 120 bytes of garbage per call (200 000 calls produced 4 gen0 collections) |
| `Node.GetPath()` | about 96 bytes per call |
| `GetParent()` for C# nodes | no garbage |
| Create, `AddChild`, `Free` 10 000 `Node3D` | about 45–48 ms |

⚠️ Remeasured during verification (same rig, Debug build with `Optimize=true`, 3 runs of 2 million calls each): `Position` set/get 49–52 ns (the first version had 65–91 ns, so the original figures were overstated by about a third or depend on machine load), `Array.Add` ×1M 84–85 ms versus 2 ms for `List<int>`, `Node.Name` 96–124 bytes per call, `GetPath()` 96 bytes, create/`AddChild`/`Free` of 10 000 nodes 42–47 ms; the other figures in the table were confirmed. Updating 10 000 transforms per frame via interop costs about 0.5–1 ms, 50 000 about 2.5–5 ms (an estimate by multiplication, not a measurement of a real scene); strings, `StringName`, `NodePath`, and Variant collections in hot paths are dangerous. This agrees with the documentation's advice to cache values and not to pass arrays and strings across the boundary: https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html . `ENetPacketPeer.Send` requires a temporary `byte[]` with no pooling (a request from the GC guide: https://github.com/godotengine/godot-docs/issues/9916 ). In 4.8 dev 2/7, non-allocating physics queries and accelerated C++ → .NET calls appeared: https://godotengine.org/article/dev-snapshot-godot-4-8-dev-7/
GC: the Godot process defaults to Workstation + Concurrent, Interactive mode (measured inside the game). `System.GC.Concurrent`, `RetainVM`, `ConserveMemory`, `SustainedLowLatency` are available; DATAS has been enabled by default since .NET 9 for Server GC: https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector , https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency . On a pure .NET server, GC can be configured freely.
The Godot profiler is oriented toward GDScript; C# needs external tools (Rider/dotTrace): https://forum.godotengine.org/t/our-experience-building-an-mmo-tech-demo-with-godot-4-4-1-net-c/134348

### F12. C# limitations in Godot: platforms, hot reload, bugs (high / medium)
- Desktop is fully supported, Android/iOS are "experimental" since 4.2, and web is not supported for C# in Godot 4: https://docs.godotengine.org/en/latest/tutorials/export/exporting_for_web.html . The reason: .NET must be the main module, just as Godot's WASM must be: https://godotengine.org/article/platform-state-in-csharp-for-godot-4-2/ . A contributor to the .NET backend (⚠️ not a "maintainer"; 2025-11-14) wrote that C# web support is in development: https://github.com/godotengine/godot-proposals/discussions/13076 ; at the time of checking, the documentation still says that Godot 4 C# projects cannot be exported to web. I know the third-party package `2dog.browser-wasm` only from a snippet (low). Decision for us: web and mobile are out of scope.
- Hot reload preserves only `[Export]` fields, and changing exported members requires a rebuild: https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html . I did not check hot reload with an external ProjectReference.
- 528 `topic:dotnet` issues are open; examples: a RefCounted leak with `LoadThreadedRequest` (#122001), a crash on exit (#119984), a crash on iOS (#124016), random crashes on scene change (#83762): https://github.com/godotengine/godot/issues?q=is%3Aissue%20state%3Aopen%20label%3Atopic%3Adotnet . Particularly significant is #118138 (opened 2026-04-02, reproduced on 4.6.2 mono under Fedora 43): interop on Linux System V x64 relies on undefined behavior (register mismatch when returning structs), the returned structs get corrupted (example: `Color.FromOkHsl` returns garbage), and it does not manifest on Windows; fixes #123842 (open, milestone 4.x) and #122907 (inactive) are awaiting review: https://github.com/godotengine/godot/issues/118138 . ⚠️ Verified only on 4.6.2 and on a specific call; not verified for 4.7.2. For a Linux server built from a Godot export this is a real risk, though not proven to be ubiquitous (it affects paths where such structs are returned through interop); a pure .NET server without GodotSharp does not have this risk.
- A forum thread about 4.6 claimed that .NET 10 features were unavailable: https://forum.godotengine.org/t/net10-and-c-14/133412 ; my test on 4.7.2 built `field` from C# 14, and I did not check extension members.

### F13. The "Kernel + client" structure (high for the base case, medium for nuances)
- Test: a `Godot.NET.Sdk/4.7.2` project + a `ProjectReference` to an independent `net10.0` library with no Godot (using `System.Numerics`) built and is called from `_Ready()` on headless Godot 4.7.2.
- Nuances from the forum: the solution name must match the assembly name of the Godot project, otherwise the editor recreates the solution; the workaround is to place it above the Godot project folder; scripts for nodes must reside in the Godot project; PR #98807 is open: https://forum.godotengine.org/t/c-multi-project-setup/56057 , https://forum.godotengine.org/t/c-multi-project-structure/128806
- The Kernel must not reference GodotSharp types: use `System.Numerics` and its own entity IDs; tests run on plain `dotnet test`.

### F14. User-generated content and mods (high)
- `ProjectSettings.load_resource_pack()` loads PCK/ZIP at runtime; for C#, the mod's DLL is loaded first via `Assembly.LoadFile`. The documentation warns about malicious code in mods and advises signing patches with asymmetric cryptography: https://docs.godotengine.org/en/stable/tutorials/export/exporting_pcks.html . There is no sandbox, and a forum question about blocking `OS` for PCK code is unanswered: https://forum.godotengine.org/t/modding-support-and-security/64752
- Conclusion (medium): DLL mods only from trusted sources; for UGC, data-driven content and scripts in the Kernel sandbox (the SS14 approach, F6).

### F15. UI (medium)
- Scaling: stretch (`canvas_items`, `viewport`), `content_scale_factor`, HiDPI, font oversampling: https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html . SS14 left in part because of scaling at 4K (2019); it has improved since then, but a prototype is needed.
- Large `RichTextLabel`s (chat, logs) cause stutter; `append_text()`, `push_*()`/`pop()` and the Threaded property help: https://docs.godotengine.org/en/4.2/tutorials/ui/bbcode_in_richtextlabel.html
- tgui (React/TypeScript in the tg repository) does not carry over; every window is rebuilt from scratch on `Control` and themes: https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html . The documentation does not describe limitations for dense windows and IME.

### F16. Voice chat (medium)
- Godot provides microphone capture (`AudioEffectCapture`, float PCM), but no codec, VAD, or jitter buffer: https://docs.godotengine.org/en/stable/classes/class_audioeffectcapture.html , https://docs.godotengine.org/en/stable/tutorials/audio/recording_with_microphone.html
- Options: Godot-Opus (a GDExtension over libopus, the catalog lists Godot 4.1, support unclear): https://godotengine.org/asset-library/asset/edit/24166 ; Concentus (pure C# Opus, about 40–50% of native speed): https://github.com/lostromb/concentus ; Steam voice via GodotSteam; RTC in EOSG. WebRTC on desktop requires a GDExtension: https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html

### F17. Anti-cheat (medium)
- Basis: an authoritative server and an untrusted client: https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html . PCK encryption requires custom export templates, and the key sits in the binary, so it is obfuscation: https://docs.godotengine.org/en/stable/engine_details/development/compiling/compiling_with_script_encryption_key.html . That managed DLLs are easy to decompile is common knowledge, but it was not checked in the sources (low). EAC is available through EOSG, but "without an example" (F4).

### F18. CI and headless (medium-high)
- CLI: `--headless`, `--import`, `--export-release/-debug/-pack`, `--build-solutions`, `--fixed-fps`, `--disable-vsync`: https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html . Dedicated server export: the `dedicated_server` tag, stripping of visual resources, the headless display driver and Dummy audio, with examples in C#: https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html
- Images: `barichello/godot-ci` (mono tags), the unofficial `liphium/godot-mono` (from search, not opened). The export documentation has no C#-specific CI guidance: https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html . A plus of the split: the Kernel and the server are built and tested with plain `dotnet`.

### F19. Project sustainability (medium)
Godot has been an independent foundation since 2022, living on donations and sponsors (Epic 250 000 USD, Re-Logic 100 000 USD and 1000 USD per month): https://en.wikipedia.org/wiki/Godot_(game_engine) . The risk is not disappearance, but breaking changes in minor versions and the slow closing of C# bugs.

## Implications for the 3D port

1. **Server without Godot.** The authoritative server = a console .NET 10 application on the Kernel. Reasons: ⚠️ the risk of an ENet/HLAPI ceiling (F2; proven only for the default configuration), the claimed but maintainer-unconfirmed vulnerability in spawn packets (F3), the interop risk on Linux x64 (F12, reproduced on 4.6.2), and free configuration of GC and threads. The conclusion about a pure .NET server remains justified even without the first two arguments (architectural cleanliness of the Kernel, no GodotSharp on the server, the unverified-in-practice scale of a Godot server). A headless Godot export is only a temporary option for the prototype.
2. **Custom protocol and replication.** LiteNetLib transport (or Steam/GNS when releasing on Steam), allocation-free serialization (pools, `Span<byte>`), interest management by chunks and radii with a per-tick budget (like PVS in SS14), deltas, priorities. Target 150–250 players at 20–30 TPS; the bottlenecks will be entity spawn/removal, physics, and snapshot assembly, not the network itself. Do not expose `SceneMultiplayer` to untrusted clients.
3. **The client as a thin layer.** Not a node per atom: entities live in the Kernel, their representations are drawn via `RenderingServer`/MultiMesh per chunk, with object pools. Set the node-count budget in advance and measure it.
4. **Lighting as a separate architectural decision.** 641–757 light fixtures on the map (Meta and Delta; ⚠️ 770–890 in the first version) and a destructible station: rule out baked light, limit dynamic shadows to the N nearest to the camera (atlas of 88), and cover the rest with "fake" light without shadows, `distance fade`. Test on Metal and on weak GPUs; choose Forward+ or Mobile.
5. **Visibility and LOS** (what the player sees, shadowing, fog) should be computed in the Kernel on the tile grid, with only the result passed to rendering; CPU occlusion culling is not the only mechanism.
6. **Pathfinding in the Kernel**, taking doors, access, atmos, and destruction into account.
7. **Physics:** decide at the design level whether server-side rigid-body physics is needed (thrown items, drift) or discrete tile mechanics are enough; if needed, Bepu or Jolt bindings on the server, with the client interpolating.
8. **C# discipline.** No strings, `StringName`, `NodePath`, or Variant collections in hot paths; structs, pools, `ArrayPool`, zero allocations in the Kernel tick. Tune the server GC after measurements. Profiling (Rider/dotTrace/dotnet-counters) from the first week.
9. **Versions.** Pin Godot 4.7.2 and net10.0 for the Kernel and server (it works locally), but before feature development verify the C# client export for Windows/Linux/macOS. Plan work for 4.8 (min net10.0); upgrade on a schedule, not on every minor release.
10. **Platforms:** desktop only; exclude web and mobile.
11. **Mods:** DLLs only from trusted sources; for UGC, data-driven content and scripts in the Kernel sandbox (IL verification and an API whitelist, as in SS14).
12. **UI:** plan for a full rework of tgui on `Control`; immediately prototype the chat (10 thousand lines) and dense windows at 4K/HiDPI.
13. **Voice:** a late stage; Opus (Concentus or libopus via GDExtension) with server-side routing by proximity and radio channels; the choice depends on the release platform.
14. **Anti-cheat:** server authority, command rate limits, validation of all actions; defer client-side anti-cheat.
15. **CI:** two pipelines: `dotnet build/test` for the Kernel and server; Godot headless import and client export in docker with a pinned version and a template cache.
16. **Spike (first 2–4 weeks):** (1) server load with 150–250 bots at 20–30 TPS; (2) station rendering with 35–50 thousand objects and about 650–760 light fixtures on target GPUs and an M-series Mac; (3) C# net10.0 export for three OSes; (4) interop with 20–50 thousand entities; (5) UI: chat and windows; (6) a voice prototype.

## Open questions (for the user)

1. Target server size and TPS: 100, 200, or 250 players? Is a pure .NET server with duplicated logic (physics, LOS) acceptable instead of headless Godot?
2. Camera: top-down / three-quarter (as in SS13/SS14) or first/third person? This determines lighting, culling, and LOD.
3. Lighting: are dynamic shadows from dozens of sources needed, or is stylized per-tile lighting enough?
4. Physics: discrete tile mechanics or full rigid-body physics on the server?
5. Platforms and distribution: Steam only? Are macOS and Linux clients needed? GodotSteam or EOS, anti-cheat, and voice depend on this.
6. Mods: data and assets, or arbitrary code? Who may upload content?
7. Voice: mandatory for release? Are proximity and radio channels needed?
8. Version: stay on 4.7.x until the game is ready, or move to 4.8 (net10.0 mandatory) right after its release?
9. Budget: are commercial solutions acceptable (Photon Fusion, Rider), or open source only?
10. Anti-cheat level: a cooperative or a competitive environment?
11. Are you ready to accept a dependency on Godot C# weak spots (hot reload, interop bugs) in exchange for a single language with the Kernel?
