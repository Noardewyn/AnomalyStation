# 04. Technical Problems of the Original (BYOND/DM) and What They Mean for the 3D Port

Research date: 2026-10-05. Baseline codebase: tgstation (shallow clone, read-only). Target stack of the port: Godot 4.7.2 mono + C# on .NET 10, with the simulation core as a separate library that has no Godot dependency.

Verdict legend for Godot/C#: **GOES AWAY** (disappears on its own), **PARTIAL** (softened, but returns in another form), **DESIGN** (requires a deliberate architectural decision), **WORSENS** (becomes our problem in the new stack). Sources "tg/..." are files of the local clone; "ref" is the official BYOND reference (info.html), downloaded and parsed locally.

## Summary

Main conclusion: BYOND gives SS13 not only problems but also a huge set of implicit free services (state replication to clients, spatial queries, line-of-sight, loc/contents containers, sound, icons, savefiles, a built-in browser for UI, player identity). Leaving BYOND removes constraints (the interpreter's single-threadedness, 32-bit memory, a closed engine with unfixable bugs, a Windows-only client), but every free service will have to be built by us. The heaviest of them is the replication layer with interest management: Godot has no ready-made spatial layer (PVS/LOS, priorities, traffic budgets), only per-component per-peer visibility filters (⚠️ clarified during verification), while in BYOND it eats 45–60% of a tick at 100 players (extrapolation from tg numbers from 2022, linearity not verified).

Problems that will go away almost by themselves: hard delete as a memory-scanning mechanism, the 32-bit ceiling, closed engine bugs, DM's float32 arithmetic. Problems that need to be designed: tick budget and simulation order, replication and prediction, an async model instead of sleep/spawn, client command security, UI, identity and bans, tests. New ones: .NET GC pauses, Godot thread safety, no built-in culling, the DoS surface of our own network stack, web UI support.

Quantitative reference points for tg (measured with grep over the clone; recounted during verification on 2026-10-05, erroneous numbers corrected): ~1.23 million lines of DM (1,228,877) in 7494 files, 140 subsystems (SUBSYSTEM_DEF and its variants PROCESSING_/MOVEMENT_/TIMER_/FLUID_/VERB_MANAGER_/AI_CONTROLLER_; the earlier "147" included 7 `#define` lines), ~1.5 thousand COMSIG signals (1514 in code/, 1556 across the whole clone; was "1504"), ~5.0 thousand RegisterSignal(s) calls (5024; the earlier "~4.7 thousand" is the SIGNAL_HANDLER count, 4677), 357 .dm files in code/datums/components (329 top-level `/datum/component/*`) and 235 in code/datums/elements (was "311" and "224"), ~3.6 thousand qdel( (3567), ~1.6 thousand addtimer( (1614), 800 do_after(, 945 INVOKE_ASYNC, 446 tgui interfaces (401 top-level files in interfaces/ — 311 .tsx and 90 .jsx — plus 45 directories), 1457 .dmi, 1108 unit-test datums. The remaining numbers, recounted during verification, agree within ±5%: CHECK_TICK 235, `set waitfor = FALSE` 116, get_turf( 4030, locate( 2438, ui_act( 462, 38 tables in the schema; individual corrections (computer_id, range/view, "BYOND bugs with numbers") are given in the corresponding F items.

## Findings

### F1. Single-threaded interpreter, tick_lag and the Master Controller — confidence: high
The BYOND server executes procedures and manages data in a single thread (ref, the Threads section for DLLs: calls from foreign threads block until the main thread handles them). By default tg runs the world at 20 FPS (TICKLAG 0.5, tg/config/config.txt); the code caps fps from above and comments that above 50 BYOND "falls apart" (tg/code/controllers/configuration/entries/general.dm). On top of the engine tg built the Master Controller: subsystems with priorities, cooperative yielding via CHECK_TICK (~230 calls), a dynamic sleep_delta, and a Failsafe "watchdog" that restarts the MC (tg/code/controllers/master.dm, failsafe.dm). The tick order is described in tg/.github/guides/TICK_ORDER.md: first the sleeping procedures wake up (the MC is almost always last), then the engine does SendMaps, and only after that are client verbs executed, so they fall outside the tick boundary and the MC does not see their cost.
**Verdict:** PARTIAL. The single-thread ceiling is lifted (atmosphere, pathfinding and replication serialization can be offloaded to workers; SS14 did exactly this with pathfinding, audio occlusion and PVS serialization), but a cooperative model with a tick budget is still needed for the main simulation thread. **New:** data races and nondeterminism, which DM by construction did not have (ref itself calls this an advantage: code is not interrupted in the middle of execution).

### F2. SendMaps/maptick and the scale of 100+ players — confidence: high (mechanism), medium (numbers, dated 2022)
After all the code has run, the engine sends changes of the visible state to the clients. Per TICK_ORDER this is ~0.45% of a tick per player (up to 0.6% on highpop), i.e. 22–30% of a tick at 50 players. Conclusion (my calculation, linear extrapolation from 50 to 100 players not verified): at 100 players 45–60% of a tick, and the tick ceiling for the MC per tg/code/__DEFINES/_tick.dm does not drop below 70% (TICK_LIMIT_RUNNING = max(100 − 2 − map_cpu, MAPTICK_MC_MIN_RESERVE=70)), so at full load the MC total is >100% and the tick stretches (time dilation). ⚠️ Clarified during verification: 70% is the lower bound of the MC ceiling, not guaranteed consumption; the MC does not always take its limit, so ">100%" is a worst case, not a constant state. tg/code/controllers/subsystem/time_track.dm shows that inside SendMaps there is a loop "per client, per tile in radius, per movable". The community's response is not a cure but restrictions: the example config has soft/hard/extreme popcap 100/150/200, and an automatic "lag switch" from 75 clients disables runechat, parallax, footsteps, ghost-zoom (tg/code/controllers/subsystem/lag_switch.dm). A Goonstation forum member (Zamujasa, post of May 2024) claims that at 150+ players tick lag is locked at a minimum of 0.6 or slower (https://forum.ss13.co/showthread.php?tid=22629&pid=202925, medium; this is a member's opinion, not a measurement); the same thread discusses a proposal for a cap of 65–70 players for RP servers (⚠️ proposal/discussion, no adopted decision is confirmed in the source).
SS14 benchmark: the April 2022 stress test — 200 players at 30 TPS with no slowdown, a peak of ~250 at 20 TPS, the developers' estimate "350+ before lag"; the bottlenecks are network rubber-banding and explosions (entity spawn/deletion and physics) (https://spacestation14.com/post/22-04-30-progress-report-33/, high).
**Verdict:** DESIGN. The cost of "reducing the state to clients" will not go away. ⚠️ Corrected during verification: the earlier wording "Godot has no built-in interest management/culling/traffic optimization" cited the page https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html, but that page simply does not mention them (absence in the text does not prove absence in the engine). Godot 4 has MultiplayerSynchronizer with per-peer visibility filters (add_visibility_filter, set_visibility_for, public_visibility, visibility_update_mode; MultiplayerSpawner honors them, https://docs.godotengine.org/en/stable/classes/class_multiplayersynchronizer.html), i.e. primitive interest management exists; what is missing is a spatial PVS/LOS layer, priorities and per-client traffic budgets. For 100+ players with 3D visibility a custom replication layer is needed (an analogue of PVS in Robust Toolbox: net.pvs, radius 25, entity enter/exit budgets, asynchronous serialization, tickrate 30 — RobustToolbox/Robust.Shared/CVars.cs, high). **New:** LOS-aware culling (otherwise wallhack), priorities and a per-client traffic budget, deltas, 3D visibility wider than tile visibility.

### F3. Input, verbs and latency — confidence: high
The BYOND client is "thin": actions arrive as verbs/Topic, are executed on the server at the end of the tick, and the effect is visible only after the next SendMaps. tg documents this: the minimum input display latency is tick_lag plus ping (tg/code/__DEFINES/verb_manager.dm). So that the MC does not suffer, tg built SSverb_manager/SSinput with a queue and thresholds of 85/95/100% of a tick; clicks are processed before movement. The keyboard bypasses .dmf macros through its own keyLoop on every tick for every client (tg/code/modules/keybindings/readme.md). Movement has no client prediction: smoothness comes from the server-side glide_size, and during a time dilation spike there is jerking (tg/.github/guides/VISUALS.md).
**Verdict:** DESIGN. For 3D (first-person or third-person camera) server-side glide will not do: client-side prediction and reconciliation for movement, interpolation of everything else, and lag compensation for combat are needed (SS14 added accounting for the target's position "from the attacker's point of view", https://spacestation14.com/post/22-11-30-progress-report-38/). **New:** divergence of prediction from the physics of tile rules (Bump/Cross/Enter).

### F4. Client rendering, icons, overlays, UI — confidence: high
Visual state consists of uniquifiable "appearances" (hashed, editing costs an unpredictable amount; tg notes cases of appearance corruption), overlays are cached manually, with a hard limit of 100 overlays per atom (tg/code/__DEFINES/overlays.dm). vis_contents is more expensive in maptick and scales with the number of players; filters and particles are cheap for the server but "potentially very laggy on the client" (VISUALS.md). Issue #83370 describes an FPS drop with several effects (smoke, steam, pollen), closed by PR #88048; #96460 — lag from particle rain. Multi-z is implemented via vis_contents and plane masters and is called "hell of our own making" in VISUALS.md; #95948 (multi-z lighting) is open. UI: tgui — React in BYOND's embedded browser (446 interfaces, 462 ui_act); on 516 this is WebView2, Windows only (https://www.byond.com/download/).
**Verdict:** GOES AWAY in part: appearance limits and the IE/WebView dependency will go away; a real 3D scene, lighting and multi-z (floors as real geometry) are solved natively. **New:** 2D sprites do not convert to 3D (assets will have to be created anew), Godot has no built-in web view (tgui cannot be carried over as is), and thousands of node objects are expensive in the SceneTree (docs: using_servers, MultiMesh/Servers).

### F5. Closed engine and unfixable bugs — confidence: high
There is no BYOND source code; the project can only hedge passively. tg has a BYOND Issue label, and the description of the Performance label reads: "Uses the 32-bit address space and slow interpreter more effectively" (https://github.com/tgstation/tgstation/labels?q=Performance). About 35 lines in the code mention a BYOND bug/problem (rough grep over .dm), but a bug or post number is given in only about 4 of them (ID 2306577 in the error handler, ID 2256651 in client_procs, forum posts 2575184 and 2611357); the earlier "~26 comments with numbers" (⚠️ not reproducible) is overstated. There is a blacklist of builds (1622 — a render bug leading to wallhack) and "not recommended" ones (1670–1671: broken in-world text; 1675–1676: frequent crashes). CI tests one pinned build 516.1685 plus the "minimum supported" 516.1659 (tg/dependencies.sh, .github/alternate_byond_versions.txt). Examples from 2025: 516.1675 crashes on login (#94810), the client browserstorage cache bloats and causes lag every 15–30 seconds (#92035, workaround — delete the file; ⚠️ the issue was closed by PR #93044, i.e. it is fixed on the tg side and does not prove "unfixability"), crashes when writing on paper (#91800, open). The other numbers (#94810 open; #83370 closed by PR #88048; #96460 closed by PR #96510; #95948 open) were checked and match the description.
**Verdict:** GOES AWAY (we own the Godot engine source and the whole simulation). **New:** Godot bugs (SS14 in 2019 began moving away from Godot 3 because of crashes, some of them related to Mono, and the lack of 2D sprite batching: https://spacestation14.com/post/19-02-20-progress-report-10/, medium: the version is outdated, Godot 4 is different). ⚠️ Corrected during verification: the earlier wording included "weak macOS OpenGL drivers" as a reason for leaving; in Progress Report 10 (23.02.2019) bad Apple drivers are named as the reason for *choosing* Godot, not for leaving, and the post describes a transition (the new Clyde renderer is optional, Godot still works), not a final abandonment. The weakness of lighting on macOS due to Apple's OpenGL drivers is mentioned in Progress Report 5 (26.02.2018, https://spacestation14.com/post/18-02-26-progress-report-5/) as a limitation, not as a reason for abandoning Godot.

### F6. A single vendor and central infrastructure — confidence: medium
Since 10 May 2025 BYOND has been under a prolonged DDoS attack: the website, the lobby and the update servers were unavailable; the "FOSS Brethren of BYOND" demanded that the code be opened; the developer refused; players connected directly to game servers by IP (https://fastnetmon.com/?p=16192 — all these points are confirmed in the source, the attack continued in June 2025, the source does not say it ended). ⚠️ The earlier "the developer, according to another retelling, considered this a personal vendetta (rutab.net/b/video-games/2025/05/27/…)" is not confirmed: in fastnetmon the "personal grudge" version is voiced by community moderators, not by the developer, and the rutab link in the report was truncated and did not open; the `byond://IP:PORT` format is not given in the source. The state after June 2025 was not verified (byond.com returns 403; see Gaps).
**Verdict:** GOES AWAY as a dependency on the BYOND hub, but **WORSENS** as our own concern: our own server list, accounts, updates and DDoS protection.

### F7. OpenDream as the community's answer — confidence: high
OpenDream is a C# compiler and runtime for DM based on Robust Toolbox; it is declared to be at an early stage, on Windows and Linux; BYOND clients and servers are incompatible with OD (https://github.com/OpenDreamProject/OpenDream). Differences (wiki): 64-bit, a built-in CEF-based browser (⚠️ the wording "Linux client on CEF" was not found verbatim in the wiki), Tracy profiler, debugger, hot reload, strict typing in development; hub calls do not work, external DLLs must be rebuilt as 64-bit, text is UTF-16 instead of UTF-8 (https://github.com/OpenDreamProject/OpenDream/wiki/Differences-Between-OpenDream-and-BYOND). tg lints code with the OD compiler in CI with the --suppress-unimplemented flag (tg/.github/workflows/run_linters.yml), i.e. the runtime is still not sufficient; OD has open bugs on tg (#2713 — static initialization order in the compiler; #2509 and #2506 — visual; search over OD issues). tg's attempt to speed up qdel under OD (PR #83236, #91771) was closed without merging: the code relies on "temporarily alive" deleted objects (in #83236 there is also a hard OD crash on /New() on a hard-deleted object), and in #91771 the author decided to look for soft-dels via weakref; OD's GC does not support refcount() (checked against both PRs). The open OD bugs on tg (#2713, #2509, #2506) were checked: all three are open; #2713 and #2509 are explicitly labeled Codebase: /tg/station, #2506 describes a bug when playing on tgstation (flashlight shadows #2509 and invisible movables #2506 are indeed visual).
**Verdict:** OD does not solve the single-threadedness of DM semantics (multithreading is not mentioned in the differences document). It is useful to us as (1) a reference server on macOS/Linux for behavior comparison (not confirmed on macOS), (2) a ready-made DM grammar parser in C# (.NET 10, like our stack). The decision to "transpile DM" is a question for the user.

### F8. Memory: 32-bit — confidence: high
DreamDaemon is 32-bit; the OD wiki explicitly states a 4 GB ceiling for BYOND. rust-g is forced to 32-bit, auxmos builds only for i686. tg catches the engine error "Out of resources!" and restarts the server (tg/code/modules/error_handler/error_handler.dm). Associative lists eat ~24 bytes per element versus 8 (tg STANDARDS.md).
**Verdict:** GOES AWAY (64-bit). **New:** .NET GC pauses and allocations in the hot path: SS14 moved from HashSet to linked lists for the sake of "memory and GC" in the event bus (Progress Report 36) and limits incoming entities per client with budgets, because entity spawning remains heavy (comments in CVars.cs).

### F9. Hard deletes, qdel and garbage collection — confidence: high
BYOND counts references and scans all memory on del(). The tg solution: qdel() + Destroy() manually nulls references, the object waits in a queue for up to 5 minutes and only then is hard deleted (tg/code/__DEFINES/qdel.dm, .github/guides/HARDDELETES.md). A dangling reference is held by vars, lists, sleeping procedures, static/global, tags, vis_contents and even the internal range()/view() caches. The engine does not say who holds the reference; tg built debugging via REFERENCE_TRACKING.
**Verdict:** PARTIAL. The expensive memory scan will go away, but leaks through strong references will remain (the GC will not collect them) and "deleted but still in someone's field" is the same state as before. **DESIGN:** entity references as handles (in Robust: EntityUid is a struct with an int Id, RobustToolbox EntityUid.cs, high), an explicit Deleted flag, weak refs where a cache is needed, a leak detector in CI.

### F10. sleep/spawn/waitfor, async and timers — confidence: high
The DM model: every sleep is a yield point, procedures "hang" (ref: waitfor, background), there are no data races, but sleeping code holds references. tg works around this: SIGNAL_HANDLER (~4.7 thousand) must be sleep-free, asynchrony goes through INVOKE_ASYNC (~940), `set waitfor = FALSE` (116), addtimer on its own timing wheel (~1.6 thousand), do_after (~800), and walk() is banned because it harms the MC (STANDARDS.md). For precise timers Goonstation moved them into a Rust library, rustick (https://github.com/goonstation/rustick). `world.time` is float32 in tenths of a second (ref: numbers are exact up to 2^24 = 16,777,216, i.e. ~19 days), `world.realtime` is rounded.
**Verdict:** DESIGN. We need our own model of "actions over time": serializable states/timers bound to simulation ticks (int64), rather than a .NET Task with a real thread. **New:** cancellation, round save/load and replication of long-running actions (progress bar).

### F11. Atmosphere — confidence: medium
In tg the atmosphere is the SSair subsystem in pure DM (a pipeline of ~9 steps: pipenets, machinery, active turfs, excited groups, hotspots, superconductivity…; tg/code/modules/atmospherics/Atmospherics.md). The document admits that there were periods when none of the active programmers understood how atmos should work. The community moved it to Rust: auxmos (byondapi, i686, releases without AVX2 are slower; open issues about Linux, https://github.com/Putnam3145/auxmos); tg does not use it (per grep). No speedup figures were found.
**Verdict:** PARTIAL. In C# one can build SoA arrays and parallel processing, but one must decide whether to reproduce the behavior bit-for-bit. **New:** balance (supermatter, explosions) depends on exact behavior; #92520 (supermatter stopped producing power) shows the fragility.

### F12. Exploits and security — confidence: high
Client entry points: Topic()/href and verbs. The BYOND reference itself warns: a player can forge a link carrying a reference to any object (ref: Topic proc). In tg: "such links are forged" (client_procs.dm), limits of 10 requests/s and 200/min (config SECOND_/MINUTE_TOPIC_LIMIT), logging of all hrefs, a ban on the client "_debug" VV, and Topic is queued like a verb. Paradise: all topic calls must be validated, SQL only parameterized (https://devdocs.paradisestation.org/coding/coding_requirements/); their exploits are divided into mechanical, server-side (rights bypass, expensive calls) and infrastructure ones (https://devdocs.paradisestation.org/contributing/exploits/). A historical href exploit on tg: issue #9809 (2015, no details).
**Verdict:** GOES AWAY in part (no forging of "object links" if the protocol is typed commands with int ids), but **DESIGN** everything else: validation and rate limit for each message type, server-side authorization. **New:** our own network stack means our own DoS surface (in Robust Toolbox they fixed a DoS in packet decryption and memory exhaustion in Lidgren; RELEASE-NOTES.md, 275.1.0 and 288.0.0); in Godot ENet/RPC "client input is untrusted" is the developer's responsibility (docs). Wallhack: information "behind the wall" must not be sent to the client.

### F13. Typing, technical debt, DM semantics — confidence: high
tg admits its debt itself: the danger of converting New→Initialize ("bugs that are found over months"), `.` as a hidden variable, associative lists; with no types in DM (var/mob/M does not enforce anything) the SpacemanDMM linter (DreamChecker) helps, and the OD compiler is also run in CI (tg/SpacemanDMM.toml, __odlint.dm). Inheritance: 311 components and 224 elements in tg are an attempt to get out of the inheritance dead end, and SS14 went further toward ECS (https://docs.spacestation14.com/en/robust-toolbox/ecs.html). A comment by MrStonedOne (author of the tg MC) on HN: a sarcastic remark that a compiled language with call overhead higher than PHP "could only be BYOND"; he is also the author of the assessment of the "one thread, many stacks" model as a strength (https://news.ycombinator.com/item?id=29109017; checked via the HN API: comments 29109513, 29122143, 29125028 confirmed). Numbers are float32, text is UTF-8 in BYOND.
**Verdict:** GOES AWAY (C# gives types, analyzers, profilers). **New/DESIGN:** for ~7.5 thousand DM content files a data-driven scheme (prototype/YAML) is needed, otherwise it will become a copy of the same spaghetti; plus the risk of "resemblance" (bug-for-bug compatibility) vs cleanliness.

### F14. Cross-platform support (macOS/Linux) — confidence: high
The official download page: a Windows client (current stable 516.1688, requires WebView2); Linux — hosting/development only, cannot be played on; macOS is not mentioned (https://www.byond.com/download/). Via CrossOver on macOS, per the CodeWeavers catalog snippet, the result is "does not install" (low: the page did not open). rust-g on Linux is built manually (RUNNING_A_SERVER.md).
**Verdict:** GOES AWAY (Godot and .NET are cross-platform; Robust Toolbox supports all three OSes). **New:** Godot C# projects cannot be exported to web, Android is experimental, iOS with caveats (https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/index.html). Practically for us: running the original on macOS (Apple silicon) for reference is non-trivial.

### F15. Database, persistence, identity — confidence: high
Rounds are ephemeral; what persists is selective (tg/code/controllers/subsystem/persistence: paintings, trophies, scars, tattoos…). The DB is MariaDB (38 tables, SQL/tgstation_schema.sql) via rust-g (async pool, up to 25 simultaneous queries: dbcore.dm). Identity: ckey from the BYOND hub, computer_id, stickyban, IP-intel (VPN check) — ~75 mentions of computer_id in 15 .dm files (⚠️ the earlier "~64" was recounted); bans and admin rights are tied to the BYOND key.
**Verdict:** GOES AWAY in part (EF/Dapper directly from C#). **DESIGN:** our own accounts, anti-ban-evasion without BYOND, serialization of the world state (if round resumption is needed), migrations.

### F16. Testing and CI — confidence: high
The tg pipeline: linters (DreamChecker, OD, grep checks, define_sanity), compilation of all maps, integration tests inside the running game for each station (~1100 /datum/unit_test), screenshot tests (visual regressions), automatic rerun of "flaky" tests (rerun_flaky_tests.yml), runs on the pinned and minimum BYOND versions. Any runtime error breaks CI (CI.md).
**Verdict:** PARTIAL. Typing will cut off a class of errors, but these will remain: headless integration tests of the simulation, golden/replay tests, fuzzing of network messages. **New:** visual tests of 3D are unstable (GPU); deterministic headless checks in the core are needed.

### F17. Implicit engine services that will have to be reproduced — confidence: medium (conclusion from the code)
tg relies on built-in operations: get_turf (~3.9 thousand), locate (~2.4 thousand), range/view/oview (⚠️ recounted: ~1.3 thousand lines by the substring `(range|view|oview|orange)(`, including derivatives like get_hearers_in_range(; ~0.7 thousand lines by the exact names of built-in procedures; the earlier "~1.5 thousand" was overstated), loc/contents containers, Move/Bump/Cross/Enter, LOS and lighting, sound(), runtime icons (/icon, GAGS). tg itself worked around the expensive parts: SSspatial_grid with "oranges ear" mobs as hearing probes (tg/code/controllers/subsystem/spatial_gridmap.dm), its own timing wheel, SSmove_manager instead of walk().
**Verdict:** DESIGN: an "inventory" of these services and their exact semantics in the tile/3D world is needed before content porting begins.

### F18. What becomes our problem in Godot/C# — confidence: high
No interest management or traffic optimization (F2); the SceneTree is not thread-safe, GPU calls only from the main thread; for tens of thousands of objects Servers/MultiMesh are needed (https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html, .../using_servers.html); a headless server exists (--headless, the dedicated_server feature, export with Strip Visuals, https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html); single-precision scene: for top-down up to ~16 thousand units are recommended, for first person 2–4 thousand (large_world_coordinates) — enough for a station of hundreds of meters; for open space and objects far from the origin (my conclusion) origin shifting or a double-precision build will be needed. SS14: "works better than BYOND SS13, but many problems" (Progress Report 36, high as a statement of the developers), network rubber-banding at 200 players, explosions. Previous ports: SS3D, RE:SS3D, UnityStation, Griefly, Bluespess; ⚠️ clarified during verification: in the HN thread (2021) this is one commenter's enumeration, and the "mechanical density of SS13" is the opinion of one participant (beaconstudios), not the outcome of the discussion; the same list includes SS14, which is alive and, per the thread, steadily progressing, so "all ports failed" is not confirmed by the source (https://news.ycombinator.com/item?id=29109017). RE:SS3D (Unity) per its README is still pre-alpha, but the repository is not archived, and the latest commits in develop are from August 2026 (https://github.com/RE-SS3D/SS3D).

## Implications for the 3D port

1. **A simulation core with its own fixed-tick loop and budget.** Repeat the MC idea (priorities, budget, measurable overrun, time dilation as a deliberate policy), but with a fixed system order and determinism. Starting target: 20–30 TPS (tg 20, SS14 30).
2. **Replication as a separate first-class module**, not "later": PVS/interest management with LOS awareness, priorities, a per-client budget, asynchronous serialization, delta compression. Build in "cost per player" metrics from day one (like world.map_cpu and time_track in tg). Target bar: 100 players without degradation, with headroom up to 150–200 (tg popcap 100/150/200).
3. **Prediction + reconciliation for movement** and interpolation of everything else; lag compensation in combat; tile "logic" must allow prediction (a deterministic subset of rules in the shared C# library).
4. **Entities as handles (int + generation)**, not direct references; an explicit Destroy/Deleted lifecycle; weak references for caches; a leak test. Decide ECS (as in SS14) versus tg's component-signal model (1504 signals map easily onto events).
5. **Replace sleep/spawn/waitfor** with serializable "actions"/timers on simulation ticks; forbid blocking calls in handlers; a single Action framework for do_after. Time is int64 ticks.
6. **Secure by default:** only typed commands with validation, a rate limit per type, server-side authorization, no information outside the visibility range, hardening of the network layer against DoS, protocol fuzzing.
7. **Identity and bans are a separate project** (accounts, anti-ban-evasion, admin panel), since the BYOND key and stickyban will disappear.
8. **Godot specifics:** the sim core without Godot, the client is a view; thousands of objects via Servers/MultiMesh; the network not on SceneTree RPC "by default" but on a custom protocol over a transport (ENet/other); UI not on web technologies by default.
9. **tg legacy as a reference, not as a specification:** community maps, atmosphere behavior and subsystems are better taken as a reference, not as a line-by-line port; decide where bug-for-bug compatibility is needed.
10. **Verification tools:** OpenDream as a reference server/source of DM parsing, headless integration tests of the simulation, golden tests, replay.
11. **Operations:** server orchestration (an analogue of TGS: watchdog, hot swap, deployment of test merges — https://github.com/tgstation/tgstation-server), our own server list and DDoS protection.

## Open questions (what the user must decide)

1. Target load and server class: 50, 100 or 200 simultaneous players? Are a popcap and a lag switch like tg's acceptable?
2. Authority model: server-authoritative with client prediction (recommended for 3D) or simplified (input → server → snapshot, as in BYOND)?
3. Keep tile logic (discrete cells, as in SS13) under a 3D view, or move to continuous physics? Prediction, atmos and collisions depend on this.
