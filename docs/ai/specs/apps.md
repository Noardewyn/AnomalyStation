# Apps: the headless server and the Godot client

Status: M0 wave 1, 2026-10-06; section 1 rewritten by M1 P3 and again by M2 P6, section 2 by M1 P6, section 3 by the M1 integration, 2026-10-07. What exists of the two programs that run the core, how to run them, and what M1 and M2 add. The server is a pure .NET process (D1, D37); the client is a Godot 4.7.2 mono project that only presents (D1, PLAN 2.10). Both run the same core libraries (`src/Core`).

## 1. Server (`src/Server`, project `Anomaly.Server`)

Status of this section: M2 P6 (the server host, the test room, the dev commands and the bots), 2026-10-07; M1 P3 wrote the first version. The server boots the translated tg world in a host-built test room, accepts players over LiteNetLib, turns each into a tg `/client` of a `/mob/living/carbon/human` that the locomotion bridge drives as a capsule (M2 P4), replicates the world to them with their private blocks (M2 P5), takes their motion frames through a jitter buffer and their actions through tg's own entry points, and logs its metrics. Design basis: the M1 scope report sections 2a-2j, the M2 scope report sections 2b, 2d, 2k, 2l, D31, D37-D40, D73, D102, D105, D106; D98's pace and glide stand-in of M1 are gone.

### 1.1 Running it

```
dotnet run --project src/Server -- --realtime                     # a live server on 127.0.0.1:7777 until Ctrl+C
dotnet run --project src/Server -- --ticks 1200 --record run.log  # 60 s of game time fast-forward, the commands recorded
dotnet run --project src/Server -- --replay run.log               # the same run again, without network; checks the final hash
```

A built server also runs as `dotnet src/Server/bin/Release/net10.0/Anomaly.Server.dll ...` (the native launcher next to it needs `DOTNET_ROOT` on a Homebrew .NET install). Exit code 0 after a run (also after Ctrl+C, SIGTERM or `quit`), 2 for a bad command line, config or replay file, 1 when a replay's final hash differs from the recorded one or the server cannot start (for example a port in use).

### 1.2 Options and the config file

The server reads `config/server.txt` (relative to the working directory; `--config FILE` names another one; a missing default file means defaults) and then the command line, which wins. The file is in tg's style (`code/controllers/configuration/configuration.dm`, `LoadEntries`): one setting per line, `KEY value`, keys in any case (the sample writes them in upper case like tg's `config/*.txt`), `#` starts a comment, a key alone is an enabled flag (or `KEY 0`/`KEY 1`); an unknown key is reported on stderr and skipped, as tg logs "Unknown setting in configuration". The repository's `config/server.txt` documents every key with its default. On the command line a key is `--key value` or `--key=value`, with `-` or `_` (`--hash-every`, `--hash_every`); flags take no value.

`world.log` lines of the tg world (the boot's "Initialized ... subsystem", the `Dm.Deferred` notes) are interleaved. Runtime errors that reach an isolation boundary go to stderr as `runtime at tick T: Type: message` (DV1). The first time a site fails (the exception type and its top frame), the line is followed by its stack (our code's frames, paths from the repository root, at most 14); after that the same site prints its line only at its 2nd, 4th, 8th, ... time, with a note (the owner's play test, 2026-10-10: a repeating runtime flooded the console without saying where it was); a running server reports a reached `Dm.NotTranslated` once per site and carries on (rules 1.4). The final line's hash is `World.ComputeStateHash()` after the shutdown tick.

### 1.4 The world

- **Boot.** `ServerHost` creates `new World(seed)`, installs its seams (the runtime sink, `world.log` to the output, `ClientSeam.SetHost`, the chat sink of 1.5), boots tg with `TgWorld.Boot` and the test room as the `compiledMap` step, and attaches the replicator. Joins open when the Master's `init_stage_completed` reaches `INITSTAGE_MAX` (tick 20): the command phase then sets `RUNLEVEL_GAME` (SSticker's job in tg, an inert stub until M10) and prints `joins open`; a Hello before that is refused with `NotReady`.
- **The test room** (`src/Core/Tg/Infrastructure/TestRoom.cs`) is built like the toy room (tg's real turf and area types, `world.turf` set before the map grows, walls placed before the area is assigned, one `/area/misc/testroom` and tg's `change_area` per turf), 48 x 48 by default (at most 64 until the boot scaling of scope risk 3 is fixed). The server rings it with `--room-space` cells of tg's space (default 3, 2026-10-13), so the room's cells are the map's moved in by that many. Two layouts (`--room-layout`, `TestRoom.IsWall` gives either without a world):
  - **`rooms`** (M2, scope 2k, the default): four rooms with a floor of r x r tiles in the corners (r = 10 at 48 x 48, smaller in a smaller map, at least 3), each walled off from the open hall that fills the rest (a plus shape) and joined to it by two 1-tile doorways without doors (doors are M3). From 44 x 44 up the hall also holds a **1-tile corridor** (18 tiles long, open at both ends: two players pass side by side in its 2 m), a **2-tile corridor closed at its east end** (the dead-end wall face to shove a player into), and six pillars; a room of 6 x 6 or more has a pillar of its own. Smaller maps have the rooms, the doorways and the hall. A flood fill over every size from 3 to 64 reaches every floor tile.
  - **`classic`**: M1's room: a rim, four short interior wall runs and a lattice of pillars, none enclosing a region.
  - Both have about 100 to 200 spawn points (a 3-tile lattice of floor cells with no wall around them, ordered by a fixed stride so consecutive joins land far apart). **Air:** every floor keeps tg's `initial_gas_mix` (`OPENTURF_DEFAULT_ATMOS`: 22 moles of O2, 82 of N2 at 293.15 K), which tg's `create_gas_mixture` turns into the turf's air once M2 P2 translates it (a deferred leaf until then); the walls block air. There is no LINDA (M4b): a breath takes a little and gives it back.
- **The avatar** (scope 2b "Stub in M1", the M10 lobby stand-in; M2): on a session's first join the command phase creates a `/mob/living/carbon/human` at the next spawn point (round robin), keys it (`ClientSeam.KeyMob`), calls `ClientSeam.Connect`, whose BYOND part attaches the new client to the mob of that key, and **registers the mob with the locomotion seam** (`LocomotionSeam.Register`, D105): from then on the bridge moves it. A reconnect finds the mob that kept its key (tg's SSD): still registered, standing where it was, solid to the others' capsules; when a session leaves, its mob gets an idle frame and stays a capsule. The dev `spawn` and the console's `spawn` of a living mob register the dummy too, so it is solid.
- **The crew stand-in** (M2 F1: stands in for the job system, M9/M10; `src/Core/Tg/Infrastructure/CrewStandIn.cs`). tg's late join names the new character from the preferences (`create_character`: a new player's `real_name` preference is a random unique name of its species) and then equips the job's outfit (`SSjob.equip_rank` → `job.equip` → `equipOutfit`). The host does the same with tg's own procs and sets nothing by hand: right after creating the avatar, before `KeyMob`, `CrewStandIn.Name` calls `fully_replace_character_name(null, generate_random_mob_name(TRUE))` (tg's form for a fresh character without records, `mining_roles.dm:243`); after `Connect`, `CrewStandIn.Equip` calls `equipOutfit(/datum/outfit/job/assistant)` (every M2 player is an assistant, tg's overflow job), whose `give_jumpsuit` takes `/obj/item/clothing/under/color/random` from `GLOB.colored_assistant` (`/datum/colored_assistant/random` while the config's `GREY_ASSISTANTS` is off), which equips a random colour jumpsuit drawn from the world RNG (one seed, the same colours). Only the uniform is equipped in M2: the outfit's other slots (ID card, headset, PDA, backpack, shoes, survival box) are deferred leaves (inventory, M4a; ID cards, M4). The dev command `spawn /mob/living/carbon/human` (`DevCommands.SpawnHuman`) and the console's `spawn` of a human call `CrewStandIn.Join` (name, then outfit), so a spawned human looks like a player. A reconnect makes nothing new.
- **tg's strings** (M2 F1; `src/Core/Tg/Infrastructure/TgStrings.cs`). tg's world start reads its name and word lists with `world.file2list("strings/...")` (`_globalvars/lists/names.dm`, `languages.dm`); the host copies those files (`TgStrings.Files`: 41 name and station lists and the two common-word lists) from the tgstation clone into the world's file seam before the boot, as it writes `config/config.txt`. The clone is found like the icons tool finds it: `$ANOMALY_TGSTATION`, else `../tgstation` next to the repository or next to the main checkout of a worktree. Nothing is copied into the repository. Without the clone the server prints one warning and players keep tg's "Unknown" (`CrewStandIn.Name` skips the name; the jumpsuit does not need the strings). A replay needs the same clone for the same names (the strings are world content).
- **A map** (M3 P2, `--map NAME`; D108, D109). The host selects the converted map (`MapSeam.Select`: its json and map
  files go into the world's file seam at tg's paths, `_maps/map_jsons/NAME.json` and `_maps/<map_path>/<map_file>`) and boots
  with `TgWorld.CompiledMap` as the `compiledMap` step (the world size BYOND takes from its compiled-in maps; no level). tg's
  SSmapping then loads the station level in its Initialize as tg does (`load_map_config`, `loadWorld`, `LoadGroup`,
  `add_new_zlevel`, `/datum/parsed_map`, `build_coordinate`), and SSatoms initializes what it made. Meta boots in about 10 s
  of Release (60 ticks including the Master's init) with a heap of about 380 MB. Players join at the turfs of tg's late-join
  landmarks (`SSjob.latejoin_trackers`); a map without any (Meta: tg's late joiners sit in the arrivals shuttle, a shuttle
  template D108 does not load) uses the turfs of its `Assistant` job start landmarks, tg's round-start spawns of the
  overflow job (`MapSeam.LatejoinSpawns`). The default stays the test room until the M3 integration makes Meta the default.
- **`--empty`** runs the bare kernel world (no tg, no room, no joins; the console's world commands are refused); `--smoke K` adds M0's smoke actors to either world. `SmokeLoad` is kept behind its flag because the loop tests of the empty world use it to make the hash depend on the scheduler.

### 1.5 Sessions and the network

A `Session` is the host's view of a player (scope 2b "Mapping"): connection, key, token, state, strikes, rate bucket, byte counters. The world never sees it; it sees tg's `/client`.

- **The Hello** travels in LiteNetLib's connection request and is checked before a connection exists: at most 256 bytes, a valid Hello (`BadHello`), the protocol version (`WrongVersion`), the name (`InvalidName`: the protocol's `NameRules.IsValid`, that is not empty, at most 42 characters counted as Unicode scalar values, tg's `MAX_NAME_LEN`, no control, format, separator, private-use or unassigned characters, not only spaces; and the host's own rules, no spaces at the ends and at least one letter or digit so its `ckey` is not empty), joins open (`NotReady`), `max_players` (`ServerFull`), more than 64 requests in one poll (`ServerFull`), a shutdown under way (`ServerShutdown`).
- **Identity and reconnect** (scope Q3): a player is a `ckey`. The first Hello of a ckey without a token gets a new server token (16 random bytes from the OS, never from the world RNG) in its Welcome. A known ckey is taken back only with its token: no token is `NameInUse`, a wrong one `BadToken`, whether the owner is connected or not (an SSD mob is held for its token; accounts come in M10). The right token while the old session is still connected closes the old one with `Replaced`; its Leave and the new Join apply in the same tick, in ordinal order. A reconnect is a new session (a new ordinal) with the player's first key.
- **States** (`SessionState`): `Joining` (accepted; the Join is queued) to `LoggingIn` (the Join applied: avatar keyed, `client/New` started, possibly sleeping) to `Joined` (`client/New` returned with a mob: Welcome, MapGrid and Snapshot of that tick went out on the State channel, then a Delta every tick) to `Leaving` (the connection ended or was closed; the Leave is queued) to `Closed` (the Leave applied: tg's `client/Del` through `ClientSeam.Disconnect`; the mob keeps its key). A drop before the Join applied removes the Join. A drop while a sleeping `client/New` has not returned still runs the Leave on that client (tg's `login.dm:2-5` warning); its late return sends nothing. A `client/New` that refuses or fails closes the session with `Refused`. The transport's timeout (LiteNetLib: 5 s) is a disconnect like any other.
- **The world closing a session.** `IClientHost.ClientDeleted` (tg deleted the client: a console kick, tg's keysend flood autokick) and a refused login close the session after the tick, with `Kicked` and the reason for a kick, `ClientDeleted` otherwise. `IClientHost.ClientMobChanged` updates the session's own entity (the Delta header).
- **Chat.** tg's `to_chat` reaches the host's message sink (presentation-seam.md section 3); a message for a client, its mob, a list of them or the world is queued per session and sent as `ServerText` on the Control channel once the session is Joined.
- **Validation and limits** (scope 2e, D40), all on the host thread inside `Poll`, before anything is queued; nothing rejected reaches the world or the replay log:
  - a message over 256 bytes is a strike, unread (LiteNetLib itself drops a client message over about 8 KB before the host sees it, protocol.md);
  - the only commands a client sends are `MotionInput` (Input channel, unreliable, at most 64 bytes, 1 to 4 frames, no unknown flag bits) and `Action` (Control channel, at most `Limits.MaxActionMessageBytes`); an unknown id, the version-1 `InputFrame`, a second Hello, a server message, or a right message on the wrong channel, a decode error, a command before the Welcome, an action with fields its kind does not use or a click without a target or button, a `MotionInput` frame more than 1200 seqs ahead of the last taken one and an `Action` tagged with such a frame: each a strike; 3 strikes within 200 ticks (10 s) close the session with `ProtocolViolation`, and its queued commands are dropped;
  - **per-type token buckets** (game time, a command over its bucket is dropped, not a strike): `MotionInput` messages `Limits.MotionInputRate` (30 per second, bursts of 15); every action `Limits.ActionRate` (20 per second, bursts of 10) and its kind's own (`ActionLimits`: rest, walk/run and combat mode 4 per second, bursts of 4; clicks 10, bursts of 5; dev commands 8, bursts of 8, since the dev menu's map tools, 2026-10-13); at most 8 actions wait for their frame (`ActionLimits.MaxPendingActions`); 30 drops of any kind within 200 ticks close the session with `Flooding`. tg's own click limits run inside the world on top (`/client/Click`);
  - a dev command while `DEV_COMMANDS` is off, or a line that does not parse, is answered with a `ServerText` to the sender and never queued (not a strike); a click or hover whose target is forged or stale is dropped in the world, counted in `Session.ClicksRejected`.
  - **Version 4 (M4a P6, protocol.md section 14).** The actions are `Click` (an entity, a turf by x, y, z, or a screen object by id, with tg's icon-x and icon-y), `Hover` and `Keybinding` (tg's drop, quick equip, swap hands, activate in hand, select hand and throw mode; a press or a release). The stateless checks above (a malformed target, an icon pixel over 32, a keybinding code outside 1 to 9 (9 since version 20), a field the kind does not use) are strikes; the stateful ones run in the command phase of the tick that applies the frame, where the world is as the player saw it (`ServerHost.TryResolveTarget`): an entity must be one the replicator shows, a turf must be tg's `locate(x, y, z)`, an entity or turf must be on the mob's level within `get_dist` 7 of it (tg's view), a screen id must be in the session's `client.screen` right now; otherwise the action is dropped and counted (`Session.ClicksRejected`), never a strike. `Keybinding` and `Hover` have their own buckets (`ActionLimits`, 10 per second, bursts of 5); a hover over its bucket is dropped silently (`Session.HoversDropped`, no flood count), and a session keeps one pending hover, so one `MouseEntered` runs per session and tick. Sessions count what the world ran: `ActionsApplied`, `KeybindingsApplied`, `HoversApplied`. tg's screentip for a hover (`on_mouse_enter`, once per tick) reaches the hovering session as a `ContextHints` message through the host's `IScreentipSink` (installed at the first join); `balloon_alert` reaches the viewer as a `ServerText` of type `balloon`.

### 1.6 The console

A reader thread hands standard input over line by line (it never touches the world or the queue); the host parses the lines between ticks (`ConsoleCommand.TryParse`). The commands that act in the world are typed commands of an always-authorized source (D73), session 0: queued for the next tick, applied in the command phase in order, and recorded. Their bodies call tg's own primitives, as tg's admin verbs do; the console's name in tg's logs is "the server console".

| Command | What it does |
|---|---|
| `spawn TYPE [X Y [Z]]` | tg's `spawn_atom` core (`code/modules/admin/admin.dm:66-74`): `new TYPE(turf)` (an `/obj` or `/mob` path; turfs change with `ChangeTurf`, M3), `flags_1 \|= ADMIN_SPAWNED_1`, `log_admin`; without coordinates at the room's first spawn point |
| `teleport NAME\|ID X Y [Z]` (`tp`) | tg's Jump To Coordinate (`code/modules/admin/verbs/adminjump.dm:35-46`) for a target: a player's mob by key or any movable by world id, `abstract_move(locate(x, y, z))`, `log_admin` |
| `list` (`who`) | the sessions with their state, mob and tg's `key_name` of the mob, like tg's `who` verb |
| `kick NAME\|ID [REASON]` | tg's boot2 (`code/modules/admin/topic.dm:216-234`): `to_chat` the player, `log_admin`, `qdel(M.client)`; the session closes with `Kicked` and the reason |
| `status` | tick, joins, sessions, queue, runtimes and the last metrics window (host only, not recorded) |
| `hash` | the state hash now (host only, not recorded; a full GC) |
| `quit` (`exit`, `shutdown`) | a clean shutdown (1.11) |
| `damage`, `heal`, `fullheal`, `kill`, `revive`, `knockdown`, `stun`, `bleed`, `blood`, `dismember`, `wound`, `gib`, `gas`, `analyze`, `speedscale`, `speed`, `godmode`, `fly`, `noclip`, `god`, `give`, `drop`, `gravity`, `breach`, `patch`, `valve`, `airmode`, `areapower`, `ignite`, `explode`, `emp`, `irradiate`, `singularity`, `delete`, `air` (and a player's `spawn`) | the dev commands (1.6a) |
| `help`, `dev-help` | the list; the dev commands' syntax |

The console logs with tg's own `log_admin` (`code/__HELPERS/logging/admin.dm:7-10`, translated by M1 P1), and tg's `key_name` names the players. The teleport reaches tg's `is_secret_level` in `/mob/abstract_move`, whose z-level look-up is a deferred leaf until M3 (no level has a trait, so no level of the test room is secret; `docs/ai/specs/not-translated.md`).

### 1.6a The dev commands (M2, scope 2k, D73, Q9)

The console types them (always allowed); a player's dev console sends them as `ActionKind.DevCommand` (a line of at most 200 bytes) when `DEV_COMMANDS` is on (by default on only when the bind address is a loopback one). They are commands like every other: a console line is a recorded Console command, a player's a recorded Action, both applied in the command phase with `usr` the requester's mob (the console: none). Each calls exactly the tg proc the table names (`Anomaly.Core.Tg.DevCommands`, host code in the spirit of tg's admin verbs, which also writes tg's `log_admin` line), so the effects, the timings (crit and death at tg's pace) and tg's messages are tg's. **The reply goes to the requester only**: the console's output, or a `ServerText` on the player's own Control channel (D40); `analyze`'s HTML is tg's own `to_chat` to the requester's mob. WHO is a player's key (a ckey match), a world id (`#123` or `123`) or `me` (the requester's mob); it must be a living mob.

| Command | tg call |
|---|---|
| `damage WHO brute\|burn\|tox\|oxy N [ZONE]` | `apply_damage(N, type, ZONE)` with a zone, else `adjust_brute_loss`/`adjust_fire_loss`/`adjust_tox_loss`/`adjust_oxy_loss(N)` (pinned: brute through `take_overall_damage` spreads over the parts); N from 0 (excluded) to 1000; ZONE is head, chest, l_arm, r_arm, l_leg or r_leg |

### 1.7 The tick, the command phase and determinism

One host thread runs the loop (scope 2e "Where the network meets the tick"); LiteNetLib's threads only move bytes, and the transport raises its events inside `Poll` only (D31). One tick (`ServerHost.RunTick`):

1. the pacer waits for the tick (`--realtime`) or returns at once;
2. `Poll()`: connection requests answered, messages validated and queued (1.5: `MotionInput` frames into the session's jitter buffer, actions into the session's waiting list), connects and disconnects queued as Join and Leave; console lines parsed and queued. Then **`FormInputs`** (1.8): each joined session's jitter buffer gives its frame for the tick, which becomes a Motion command when it differs from the one before, followed by the actions whose frame has been taken;
3. `World.Step()`: the Master's drain (every subsystem fires), then the **command phase**, a world phase (`World.AddPhase`; BYOND's step 6, verbs after the MC, waiting-model.md 7.1): the due commands in (session ordinal, seq) order, each an isolation boundary, with `usr` the session's mob (the avatar for a Join); Join runs the avatar step, `ClientSeam.Connect` and the capsule registration, Leave `ClientSeam.Disconnect` (after an idle frame), Motion the locomotion seam's frame, Action tg's own entry point (rest, walk/run, combat mode through the keybindings' `down`, a click through `ClientSeam.Click`, a dev command), Console the console's world command or dev command. **Right after it the locomotion phase** (`LocomotionSeam.Install`, M2 P4) steps every registered capsule in `dm_id` order: the gate, the controller, tg's `Move` at each tile crossing;
4. after the Step, the host checks the logins that finished, and the replicator builds the tick's Delta once (read-only, outside the world), the join messages (with the session's private block) of the sessions whose login finished, and then **each joined session's private block** (`BuildPrivate` from `PrivateInputs`: its client's world id, the capsule state and parameters from `LocomotionSeam.TryGetState`, the last acknowledged frame and the jitter buffer's depth after the tick);
5. the host sends the Deltas (a per-session header and private block on the shared body: `Codec.EncodeDelta(..., body, ownBlock, ...)`), the join sequences, the chat and the dev replies, closes what must close, and flushes the transport;
6. metrics (including whether SSmobs fired in the tick).

**Determinism** (scope 2j). A command received while tick T is the last stepped applies at T + 1 (the Step of the same `RunTick`). Within a tick commands apply in (ordinal, seq) order whatever their arrival order: a Motion command carries its frame's seq, an action the seq of the last frame taken (so it sorts after that frame's Motion), a Join is seq 0 and a Leave the largest seq of its session, console commands are numbered from 1. What the command phase does in the world depends only on the applied commands and the world, never on a session's network side (its jitter buffer, buckets or acknowledgement), and host randomness (the tokens) never enters the world; so a replay of the recorded commands gives the live run's world. One detail keeps that true: the idle frame a leaving session's mob gets carries the seq and yaw of the last Motion *command* (a world-half field), not the network side's acknowledgement, which also follows the frames that were no command.

### 1.8 The input path and the speed (M2; D98's pace and glide stand-in of M1 are gone)

The avatar is a living mob moved by the locomotion bridge at tg's own speed (`cached_multiplicative_slowdown`, D106), so M1's pacing of held keys (D98) and its glide for a plain `/mob` are removed; tg's `keyLoop`/`client/Move` path stays for the mobs the bridge does not drive (DV14).

- **The jitter buffer** (`InputJitterBuffer`, one per session; scope 2d). Every `MotionInput` message repeats the client's last 4 frames, and the unreliable channel may deliver them late, twice or out of order. The buffer keeps a frame once, in seq order (a frame whose seq is not above the newest offered is a repeat and ignored); the host takes **one per tick**; with none queued the last taken frame repeats, with its seq (so `lastInputSeq` does not advance), and after 10 repeated ticks (half a second of silence, `ActionLimits.MaxRepeatedFrameTicks`) the host sends an idle frame in its place so that a client that went silent does not run into a wall for the 5 s its connection takes to time out; with more than 4 queued (`Limits.MaxJitterBufferFrames`; 3 until the M2 integration, whose measurement is in `Limits`) the oldest are dropped first (`Dropped`), so input is never delayed by more than 4 ticks. The depth after the take goes into the private block (the client's input clock aims for about one queued frame). A seq more than 1200 ahead of the last taken refuses the whole message (a strike).
- **Motion commands.** The taken frame is recorded as a `CommandKind.Motion` command of the tick (the replay needs no buffer) when its wish or yaw differs from the last frame queued for the session; an unchanged repeat is no command, because the seam keeps a mob's last frame, but its seq is acknowledged all the same. The command phase calls `LocomotionSeam.SetFrame` with the session's mob; the locomotion phase that follows steps the capsule with it.
- **Actions** (rest, walk/run, combat mode, click, dev command) arrive on Control tagged with a frame seq and **apply in the tick that takes that frame**, after its Motion command (so a click sees the capsule where the player saw it), or in the next tick when the frame was already taken. Rest, walk/run and combat mode are tg's keybinding path for one key press (`ClientSeam.Rest`, `ToggleMoveIntent` as `toggle_move_intent_alternative`, `ToggleCombatMode`: `can_use`, `down`); a click is `ClientSeam.Click(client, target, ClickParams(button, shift, ctrl, alt))` after the host checked that the target is an entity the replicator shows; reach, the cooldown and the shove are tg's `ClickOn` chain (M2 P4) and `disarm` (M2 P1, DV17).
- **Speed.** `MOVE_SPEED_SCALE` (default 1.0) is set on the seam at boot and by the dev command `speedscale`; the seam turns tg's slowdown into tiles per tick (`0.5 / slowdown * scale`). The scale is world state, so a replay needs it: the log records it (1.9) and the dev command is a recorded command. Running at scale 1 is 13.3 m/s at 2 m tiles.

### 1.9 The replay log

Every applied command (Join, Leave, Motion, Action, the console's world commands and dev commands, the shutdown) is kept in memory in application order (`CommandLog`). `--record FILE` writes it as it applies, with the seed, the room and its layout, the smoke load and the speed scale, and at shutdown the final tick and state hash (format 2; an M1 log, format 1, is refused):

```
# Anomaly.Server command log: the commands the world applied (docs/ai/specs/apps.md section 1)
format 2
protocol 2
seed 1
empty 0
room 48 48
layout rooms
smoke 0
speedscale 1
movedelay 1.5 4
map metastation
c 21 1 0 Join - :Alice
c 23 1 1 Motion m100,-20,12345,0 -
c 24 1 1 Action a1,0,0,0 -
c 25 1 2 Action a4,1028,2,0 -
c 26 1 2 Action a5,0,0,0 :damage me brute 5 chest
c 40 0 1 Console - :spawn /obj 10 10
c 52 1 4294967295 Leave - -
c 400 0 2 Console - :quit
end 400
hash 0123456789ABCDEF
```

The `map NAME` line (M3 P2) is written only for a map run (`--map`), so a room run's log is unchanged; a replay loads the map of
that name from its own `--maps-folder`. Fields: apply tick, session, seq, kind, an extra field and the text (`-` for none, else `:` and the text with `\\`, `\n`, `\r`, `\t` escaped). The extra field is `-`, `d` and the held directions (M1's `Input`, never produced now), `m` and `moveX,moveY,yaw,flags` (a Motion frame), or `a` and `kind,target,button,modifiers,targetKind,x,y,z,iconX,iconY,keybinding,keyUp` (an Action; the kind numbers are `ActionKind`'s; the last eight values are version 4's, M3's lines have the first four and read as before: a click with a target and no kind is an entity click). `--replay FILE` builds the same world, feeds the commands to the same command phase without network or console (through the same locomotion seam, `ILocomotionEntryPoints`), runs fast-forward to the end tick, prints the final line and compares the hash: `replay: the final hash equals the recorded one`, or `MISMATCH` and exit code 1.

### 1.10 Metrics

Per tick (scope 2i): the world step, replication (Delta and joins), network poll and send (including the flush), the total, and the pacer's lateness and overruns, and (M2, scope 2l) the world step of **the ticks SSmobs fired in** (every 40 ticks it runs every living mob's `Life` in one tick, which never yields, DV3: the peak tick of a 150-bot run; the `mobs-tick` figure of the status lines and the summary, the `mobs_fired` CSV column), each in an allocation-free histogram with fixed buckets (exact below 64 µs, 32 per power of two above: at most about 3% above the true value) for the current window (`--status-every`, 200 ticks) and for the run, reported as p50, p95, p99, p99.9 and max in milliseconds; bytes per session per second from the host's own counters (payload) and from the transport's (`IChannelCounters.WireBytes*` where the transport measures its headers and acks, LiteNetLib's statistics; else its payload counters); GC counts per generation, the total GC pause, the bytes the host thread allocated per tick, the heap size. **`click_ms`, the server's part** (M4a P6; `ServerHost.ClickLatency`, `ClicksTimed`): for each click the world applied, the time from the click's arrival on the host to the end of the Delta sends of the tick that applied it (the ticks it waited for its frame, the step with tg's chain, the replication, the encode and the send), in the same kind of histogram; the client's part is added by the Godot client (`click_ms` beside `ack_ms`, I1 reports both). A `status` line per window, a summary at shutdown, and with `--metrics FILE` a CSV row per tick (`tick,poll_us,step_us,replication_us,send_us,total_us,lateness_us,overrun,sessions,bytes_out,bytes_in,alloc_bytes,gc0,gc1,gc2,heap_bytes,mobs_fired`, formatted into a reused buffer). The host sets `GCSettings.LatencyMode = SustainedLowLatency` in real time and never calls `GC.Collect`; the state hash, which forces full GCs, runs only with `--hash-every`, the console's `hash` and once at shutdown, outside the tick's timing.

### 1.11 Shutdown and pacing

- **Clean shutdown.** Ctrl+C (SIGINT), SIGTERM and the console's `quit` request a stop; the next tick is the shutdown tick, whose command phase applies a recorded `quit`: every client's connection ends in the world (tg's `client/Del` through the seam, in ordinal order) and tg's `world/Del` runs (M1 P1 translates it). After the tick every connection is closed with `ServerShutdown`, the transport stops, the record file gets its end and hash, the CSV is closed, and the final and summary lines are printed; exit 0. `--ticks N` runs the same shutdown in tick N. A second Ctrl+C kills the process at once. A background job of a non-interactive shell inherits SIGINT as ignored; scripts stop the server with SIGTERM.
- **Real time** uses a `Stopwatch` in the host (the core has no clock, D31, DV3): one tick every 50 ms. The pacer sleeps until 6 ms before the tick and yields the rest (a timed wait alone oversleeps by about 5 ms on macOS); a tick that starts late by less than a tick keeps the schedule, and after an overrun of a whole tick the schedule restarts from now instead of a burst of catch-up ticks (BYOND: an overtime tick "still only counts as one tick").
- Measured (M1 Pro, Release, no players, 48 x 48 room): a fast-forward run of 300 ticks with boot takes about 1.5 s of process time; an idle tick costs about 0.02 ms and allocates about 3 KB; real-time lateness p99 under 0.1 ms on a quiet machine, up to about 9 ms under load from parallel builds.

### 1.14 The bots (`tools/Anomaly.Tools.Bots`, version 2)

Headless protocol clients (D55) that move capsules: each update (20 a second) a walking bot sends one `MotionInput` message with its newest 4 frames (a wish vector up to 127 and a yaw) on the Input channel, and its discrete actions as `Action` messages on Control tagged with the newest frame's seq. Behaviours: `wander` (a compass heading in continuous space, looking ahead along it in the replicated solidity grid with the capsule's radius and steering away from walls; re-picked when the position stops changing; 1-tile corridors and dead ends are walked out of), `rest` (lies down every 5 to 15 s for 3 to 6 s, and now and then presses walk/run and combat mode), `shove` (walks the straight line to the nearest standing body it can see within 10 tiles and right-clicks it within 1.5 tiles, one click per 20 ticks), `mixed` (wander, rest, shove, wander by index), `idle`, `churn`, and the abusive modes (`abuse-flood`, `-action-flood`, `-forged-seq`, `-malformed`, `-bad-action`, `-dev`, `-oversized`, `-early-command`, `-wrong-version`), each making exactly the violation it names. Version 4 (M4a P6) adds `fiddle` (wanders and, four times a second, hovers, picks up the nearest item, uses it, swaps hands, drops, throws at a random cell, shift-clicks the nearest thing and clicks its own HUD entries: load and soak for the interaction base) and the abuse modes `abuse-forged-target` (well-formed clicks and hovers on ids no world has, on turfs of other levels, on entities out of view, on screen ids it does not own: dropped silently), `abuse-hover-flood` (15 hovers a second: the surplus is dropped, the session stays) and `abuse-bad-v4` (raw actions that break the format: strikes). With `--predict` a bot predicts its own capsule with `MotionPredictor` and `InputClock` (the headless prediction client) and counts reconciliations, corrections, snaps and bit mismatches; its view leaves its own entity out of the replica's capsules (`SelfExcludingView`), because the predictor does not know which entity is its own. The planners (`WanderPlanner`, `ShovePlanner`, `RestSchedule`, `BotDriver`) are functions of plain values behind `ISolidity`, tested without a replica or a codec. Usage, the report's fields and the soak script are in `tools/soak/README.md`.

### 2.2 Build settings and the target framework (unchanged since M0, plus the M1 and M2 references)

- **TFM.** D77 pins `net10.0`, and it works with Godot 4.7.2: Godot generates `net8.0` (its minimum, `GodotTools ProjectGenerator.GodotMinimumRequiredTfm`) but accepts any higher TFM, and `net10.0` is needed to reference the `net10.0` core libraries. Verified: `dotnet build`, Godot's own build (`--build-solutions`), the headless run and the windowed render all work on Godot 4.7.2.stable.mono with .NET SDK 10.0.401 (runtime 10.0.12, the only runtime installed). `TargetFramework` must stay in the `.csproj` itself: when the editor finds none there it adds `net8.0` (`ProjectUtils.EnsureTargetFrameworkMatchesMinimumRequirement`). The editor left the committed files untouched on open, import and build.
- **`godot/Directory.Build.props`.** MSBuild imports only the nearest `Directory.Build.props`, so this file stops the inheritance of the repository-wide one (whose settings are for the core, server, tools and tests) and sets the client's own: the same conventions (latest C#, `Nullable` disabled, no implicit usings, the global usings `System` and `System.Collections.Generic`, CS4014 as an error for the waiting model) without `TargetFramework` (above) and without `InvariantGlobalization` (a runtimeconfig setting; Godot hosts the runtime itself). The core projects the client references still build with the repository-wide file. For the record, inheriting the repository-wide file also builds today; the separate file keeps future core-only settings (analyzers, warning sets) out of the Godot project.
- **Configurations.** Godot builds the project as Debug (editor), ExportDebug or ExportRelease; the core projects know only Debug and Release. Godot 4.7.2 itself always builds and publishes the `.csproj`, not the solution (GodotTools `BuildSystem.BuildArguments` and `BuildPublishArguments` pass `BuildInfo.Project`). For that path an item definition on `ProjectReference` (it reaches the transitive references too) maps ExportRelease to Release and the others to Debug, so the core's output stays in `bin/Debug` and `bin/Release`. The `dotnet publish` step of an export, run by hand with the arguments `BuildPublishArguments` passes (`dotnet publish godot/Anomaly.Client.csproj -c ExportRelease -r osx-arm64 --self-contained true -p:GodotTargetPlatform=macos -o DIR`), builds the core RID-agnostic into `bin/Release` and puts it into DIR next to the client; a full export (export templates, the packed game) was not tried. A build of `godot/Anomaly.Client.sln` (an IDE, or `dotnet build godot/Anomaly.Client.sln -c ExportRelease`) ignores that mapping for projects that are not in the solution: MSBuild then drops `Configuration` and builds them with their default, Debug. So the solution lists the core projects (Kernel, DmShim, Tg) with the same mapping (ExportRelease to Release, Debug and ExportDebug to Debug). A new core project that the client reaches must be added to both `AnomalyStation.sln` and `godot/Anomaly.Client.sln`. The solution must exist: when the editor's build finds no `.sln` or no `.csproj`, it regenerates both from Godot's template (`GodotSharpEditor.CreateProjectSolutionIfNeeded`), which would drop `net10.0` and the core reference. The editor rewrites an existing solution only to migrate Godot 3 configuration names (`DotNetSolution.MigrateFromOldConfigNames`, which looks for `Tools|Any CPU`).
- **References.** The client project references `src/Core/Tg` (and through it DmShim and Kernel), `src/Protocol` (the wire protocol and `ReplicaWorld`), `src/Net` (the transports; LiteNetLib 2.1.4 comes through it) and, since M2, `src/Core/Motion` (the capsule controller, the predictor and the input clock, D103). `godot/Anomaly.Client.sln` lists all of them with the ExportRelease mapping; `dotnet build godot/Anomaly.Client.sln -c ExportRelease` builds Protocol and Net as Release. The client's own code under `godot/scripts/Shared/` uses no Godot API and is also compiled, as linked files, into `tests/Anomaly.Server.Tests` (2.7).
- **Not in `AnomalyStation.sln`.** The client is built by Godot or by `dotnet build godot/Anomaly.Client.csproj`, never by `dotnet build AnomalyStation.sln`, so the root build and `dotnet test` need neither Godot nor the Godot NuGet packages.

### 2.3 What is drawn

- **The map and the entities** are drawn as 2.9 says (M2 P7: the tg-textured turf kit, billboards from tg's icons, lying quads; the M1 capsules and boxes remain as placeholders for what has no appearance or no converted icon). - **No name plates** (D56): names are in the HUD's counts only and in the optional names overlay (F3, `--names`).

- **The camera layer** (D41: a replaceable layer; `Play/CameraLayer.cs`): the eye is at 1.5 m standing (D137, amending D120's 1.2 m and D101's 1.6 m; the one setting `WorldScale.EyeHeight`; getting up takes about 0.4 s at 2.5 m/s) and about 0.5 m lying, easing between them in about 0.4 s. **Head bob** follows the distance walked (a cycle per 3.2 m, at most 2.6 per second, 3.5 cm up and 1.8 cm sideways at full effect, smoothly in and out with the speed) and **camera shake** is a decaying wobble that a correction of 0.15 tile or more (a shove; not while weightless or unable to move, as carried on a pulled bed, and only the first of corrections that keep coming within 2 s, as the wind's pushes), a knockdown and new damage on the doll start; both have an off switch in the options (D70) and neither moves anything the server sees. **Zero gravity** (M4c slice 7, D146, D70, DV42): while the own body is weightless (the `ZeroG` driver) there is no walk bob; the eye **floats** instead, by tg's floating animation (`DO_FLOATING_ANIM`: 2 pixels, 1 s up and 1 s down, so 2/32 of a tile, 12.5 cm at 2 m tiles, peak to peak, every 2 s), eased as a sine and fading in and out over a second (`STOP_FLOATING_ANIM`'s settle), and, when switched on, the view **leans** into a sideways glide (up to 4 degrees at 10 m/s across the view, with a slight sway on the float). The crosshair opens into four ticks over a mob, green when it is on the own tile or a neighbouring one (tg's `Adjacent`, which the server checks again, D40), amber when further. The click is an `ActionKind.Click` with the target's id, the button and the shift, ctrl and alt state. Left click with the help binding, right click with the shove binding.
- **Actions** (`PlaySession`): rest, walk/run, combat mode, a click and a dev command are `ActionMessage`s on the reliable Control channel, each **tagged with the seq of the newest frame pushed**, so the server applies it in the tick that applies that frame, with the capsule where the player saw it (scope 2d). Nothing is predicted for them (the speed after a walk/run press and the posture after a rest arrive in the next private block, one round trip later).
- **The input path.** The M1 `InputFrame` (held tile directions, quantized view, `ViewInput`'s mapping) is no longer used by the play loop; the server's `MotionInput` replaces it (2.5). `ViewInput.cs` stays for the free camera's key reading, `--autowalk` (which speaks tile directions, turned into view-relative keys) and its tests.

### 2.5 Prediction, the input clock and the drawn poses (D103, scope 2d and 1.6)

**The own capsule** (`Play/OwnPrediction.cs`, over `Anomaly.Core.Motion`'s `MotionPredictor` and `InputClock`):

1. **One `MotionInput` per tick.** Each rendered frame the session reads the held keys and the view yaw and turns them into the world-space wish vector (`MoveWish`: east and north components of at most length 1, so a diagonal is as fast as a straight line; the wire's yaw is a compass bearing, the negative of Godot's). The input clock (`InputClock`, nudged by up to 5 % so that about one frame, two on a network that is not localhost, waits in the server's jitter buffer) says when a frame is due; the frame carries the keys' **time-weighted** wish over the tick that just ended (a key held for 40 % of a tick is 0.4 of full speed; the wire's wish is analog), the frame is stepped through the predictor (`Push`: the same `MotionStep.Step`, the newest parameters the server sent, the collision view) and sent with the three before it (`CopyRecentFrames`, four-frame redundancy) on the unreliable Input channel.
2. **The camera draws more than the last tick.** `RenderPosition` is the newest predicted state, plus the visible error still decaying, plus a **render-only partial step** of the tick in progress: the same integral of the keys so far, run through the same step and never stored. A key shows on the next frame, and at the tick's end the partial step equals the one the frame makes, so nothing jumps back on a release or forward at the boundary (`OwnPredictionTests`).
3. **Reconcile on every private block.** `ReplicaWorld.OwnStateReceived` calls `OnOwnState`: the first block with a capsule starts the predictor from the server's state; every later one resets to the state after `lastInputSeq`, replays the later frames and compares (under 1 cm nothing, up to a tile the error decays over 100 ms, more snaps, but while the server's state slides (tg moved the mob) up to 3 tiles still decay; `Corrected` raises the camera's shake). A shove, a knockdown and a slowdown arrive in the block and are replayed as the state they are.
4. **The collision view** is the replica's (`ReplicaWorld.CollisionView`: the map's solidity bits and the other standing capsules at their newest received position, the default radius, lying ones left out) **with the own entity taken out** (`OwnExcludingView`): the predictor's `Step` does not know the own id and the replica holds the own entity a round trip in the past.
5. **Measured** (headless, over the loopback, the scripted server running the real controller): walking alone gives zero corrections, zero snaps and zero mismatched bits at 0, 50, 100 and 200 ms of one-way latency; with 2 % of the Input messages lost a correction happens only when the server's buffer ran dry (two messages in a row are lost) or overflowed (a burst after a loss), about once in two minutes of walking (30 seeds of 60 s: 40 % had one; `HeadlessPredictionTests` asserts that every correction is explained by such a server-side event); a shove corrects once, 0.66 tile at 100 ms, and the counters stop growing at once; a contact with a wandering body corrects by under a tile and never snaps.

**The other entities** (`Play/PoseSource.cs`, `Play/Interpolation.cs`; replaces M1's tile glide for capsule mobs, scope 1.6):
- A capsule mob sends its continuous position, yaw and posture in every tick it changes (`Pos`, `Yaw`, `Posture`). A sample `(T, p)` means "after tick T the entity is at p": between samples of consecutive ticks it moves in a straight line; between samples further apart it stands still until the last tick before the later one. The newest sample is **held**; when the client has no newer tick than that sample's (a late Delta) it is **extrapolated by at most one tick**, and past that held again. A jump of more than 2.5 tiles, or to another level, is a teleport. Items and other movables keep the replica's M1 glide.
- **The render clock stops at the data** (`RenderClock.Update(now, latestTick)`): it still follows the newest tick minus about 2 ticks at +-10 % speed, but it slows down as it passes the newest tick for which there is data and never goes more than a tick beyond it, so a late Delta is not followed by a jump.
- **The visible-error limit** (`PoseSmoother`): a pop of the target (a catch-up after a stall) is closed at no more than 9 tiles per second or 1.4 times the entity's own speed, never faster than any frame of a plain run, so no frame shows an entity at several times its speed. 9 tiles per second is 18 m/s; the run is 13.3.
- **The hitch's measure** is the 99th percentile of the per-frame speed of every drawn mob (`FrameSpeedStats`: the distance moved over the frame's real time, in m/s, teleports left out), reported in the summary as `p99_speed` (others) and `own_p99_speed`, with `peak_speed` kept for M1's comparisons. In M1 the worst frame was 90 and 116 m/s over 30 minutes. Measured now (the scripted world, 12 bots wandering for 45 s, a headless run of the tests and 40 s Godot runs with 40 bots): p99 13.5 m/s at 15, 30 and 144 frames per second, with a jitter of 30 ms or stalls of 135 ms and 300 ms of the link, whose worst frames stay under 20 m/s; Godot with 40 bots at 15, 30 and unthrottled frames per second: p99 13.8, 14.5 and 14.8 m/s, peak 16.1, 19.5 and 16.2 m/s (the first second runs the render clock 10 % fast to settle).

### 2.6 The HUD, the console and the options

- **The health HUD** (D107, amends D44; `Hud/HudLayer.cs`). ### 2.7 The engine-free logic and the fake world

`godot/scripts/Shared/` (with `Play/`) has no Godot API (`using Godot` is forbidden there): the files are compiled into the client and, linked (`LinkBase="ClientShared"`), into `tests/Anomaly.Server.Tests`, whose `Client/` folder tests them: the arguments and the input script, the options and key bindings, the wish vector, the interpolation (sample evaluation, the smoother, the speed statistics, the render clock that stops at the data), the camera layer, the pick, `screen_loc`, the doll's zones and cues, the console model, the own prediction glue (frame cadence and redundancy, the partial step, reconciliation, the input clock's nudge), the play session (action tags, poses, statistics, the free camera), `GameClient` (scripted transport; end to end against P5's `MiniServer` and the scripted server over the loopback; real sockets), the simulated network, and the fake world.

The scene code reads the world through `IWorldFeed`, whose entities are `ReplicaEntity` objects of a real `ReplicaWorld` (`Replica`: the tables, the own private state, the screen entries, the collision view). `GameClient` is the real feed (`SendMotion` on the unreliable Input channel, `SendAction` on Control; the M1 `SendInput` and its `InputFrame` are gone since the M2 integration); `FakeFeed` is the scripted world behind `--fake-server`, version 2: a `FakeServer` (a 20 TPS room of capsule mobs that speaks protocol version 2 and **runs the real controller, `MotionStep`, with the real parameters**, so the client's prediction can be checked bit for bit; the jitter buffer; rest, walk/run, combat mode, the help click and the shove with the click cooldown, a knockdown with the automatic get-up; the player's HUD as private screen entries with tg's doll states and the dev commands in the real server's syntax) whose messages go through the real `Codec` after a simulated one-way delay with jitter into a real `ReplicaWorld`, and the client's frames and actions go back the same way (`--sim-latency` and `--sim-loss` add to it). So the renderer, the prediction, the HUD, the console and the byte counts are the real ones; only the server's world is scripted. The same `FakeServer` runs behind a `LoopbackNetwork` in the headless prediction tests (`HeadlessWorld`: `GameClient` over loopback transports with latency and loss, `PlaySession` on top, one tick per network step).

### 2.9 Rendering (M2 P7: tg's icons, billboards, the turf kit; D104)

Mobs and items are Doom-style billboards made from tg's own sprites, composed from the replicated appearances; walls, floors and the ceiling are simple geometry carrying tg's turf pictures. This section replaces the "capsules and boxes" of 2.3 (the capsule and the box stay as placeholders for an entity that has no appearance or whose icons are not converted).

**The icon tool** (`tools/Anomaly.Tools.Icons`, `--tg <tgstation> --out <dir>`, default output `godot/assets/tg`, git-ignored until D88's infrastructure pass). Every `.dmi` under tg's `icons/` becomes `<icon path>.png` (the file's own bytes: a DMI is a PNG, and the extra zTXt chunk is ignored by PNG readers) and `<icon path>.json`: width, height, sheet size and per state its name, `dirs`, `frames`, `delays` (deciseconds), `loop`, `rewind`, `movement`, `hotspot`, `first` (index of its first frame) and `rects` (`dirs * frames` rectangles `[x, y, w, h]`, direction-major: the frame of direction d, animation frame f is `rects[d * frames + f]`; directions are in file order south, north, east, west, then southeast, southwest, northeast, northwest). Every GAGS config (`code/datums/greyscale/config_types`: the DM types, inheriting `icon_file` and `json_config` by type path, `#define`d icon files resolved) becomes `gags/<type path below /datum/greyscale_config/>.json` (`jumpsuit/worn.json`: type, name, icon file, and tg's own JSON as `states`) plus `gags/index.json`. A second run writes nothing (files already holding the bytes are skipped). 1448 icons (48691 states) and 325 configs convert in about 2 s, 61 MB. The output carries a `.gdignore`, so Godot never imports it: the client reads the files itself (`IconPaths.Root`, override `ANOMALY_ICON_ROOT`). The art is CC BY-SA 3.0 (tg README); `godot/assets/tg/SOURCE.txt` says so. `tools/convert-tg.sh` runs the tool (`ANOMALY_TGSTATION` names the clone; default: a `tgstation` folder next to the repository or a parent).

**The client's pipeline** is engine-free (`godot/scripts/Shared/Icons/`, also compiled into `tests/Anomaly.Server.Tests`), so everything below but the last two bullets is tested without Godot:

- `PngDecoder` (every colour type and depth, tRNS, Adam7) and `Raster` (RGBA8; BYOND's `icon.Blend` modes add, subtract, multiply, overlay, underlay, and, or; tints; colour matrices).
- `IconLibrary` (the IconAtlas): a resource is `icons/obj/doors/airlock.dmi` (the converted `.png` and `.json`, decoded lazily and kept; frames are cut out on first use) or `gags:<config type>|<colours>`. A miss is remembered, a problem (missing file, state or config) is recorded once (`Problems`, logged as a warning by the client).
- GAGS (`GagsConfig`, `GagsIcon`): tg's `GenerateBundle` one state at a time on first use: `icon_state` layers multiplied by their colour, `reference` layers (another config generated with this layer's colours), `color_matrix` layers (the layers below mapped), nested groups joined with the first layer's blend, blends by direction and frame (a layer with one direction serves all). Colours are tg's `#rrggbb#rrggbb` string. The jumpsuit worn at `#3f3f3f` is tested pixel for pixel against the same picture computed straight from the two source states, and every state of all 325 configs composes. **Assumption (P3 decides the var):** the icon of a GAGS appearance is the text `gags:<config type path>|<colours>` with `icon_state` the state of the generated bundle (`jumpsuit`), as `replication.md` section 6 and `AppearanceEntry.Icon` say; the colours may also come in any text that has the `#rrggbb` runs. A config asked for more colours than it was given (tg's own gold cleric mace does this through a reference) uses white for the missing ones and records a problem.
- `AppearanceCompositor`: an interned appearance and its overlays and underlays composed for one direction, cached per appearance (public or private reference) and direction, animated ones composed again only when a frame changes. Rules (BYOND ref): children sort by layer, a float layer (negative, tg's `-BODYPARTS_LAYER` indexes) above the parent and among floats by value, any other layer absolute against the parent's, equal layers in list order, underlays below the parent, nesting compared level by level so a child's overlays stay with it; a child inherits the parent's colour (multiplied, matrices composed), alpha and transform (child first, then parent, each about its icon's centre) unless `RESET_COLOR`, `RESET_ALPHA`, `RESET_TRANSFORM`; `pixel_x/y` move the child inside the parent's transform and `pixel_w/z` after it; `KEEP_TOGETHER` (tg's humans have it) composes the group first and then applies colour, alpha and transform to it, `KEEP_APART` children stay out; `blend_mode` 0 is the parent's, add, subtract, multiply and inset overlay change how a child joins; a child without an icon uses its parent's; transforms sample nearest (`PIXEL_SCALE`). The result is a picture plus where the atom's 32 x 32 square sits in it (a lying human's translated sprite or an overlay's pixel offset reach out of the square). **Not followed:** planes beyond ordering (lighting and emissive planes are not ported, DV12), filters, maptext, big icons' offsets, invisibility. **Assumption:** `AppearanceEntry.ColorMatrix` is BYOND's 20-number list in list order (rows red, green, blue, alpha, constants; columns r, g, b, a), which is what `replication.md` section 6 says the server completes 9, 12, 16 and 20 number lists to.
- `BillboardMath`, `TurfKitPlan`, `ShowcaseWorld` (below).
- Godot side (`godot/scripts/Render/`, `EntityLayer.cs`, `MapRenderer.cs`): `AppearanceTextures` (the `IAppearanceTextures` of the contract: the library, the compositor and the engine textures, one upload per picture, a new replica starts the caches again), `Billboard`, `IconPaths`, `ReplicaTables`, the showcase.

**Billboards.** One quad per entity with a picture, a `ShaderMaterial` of `shaders/picture_billboard.gdshader` (M3 I1c; it was a `StandardMaterial3D`) with a Y-axis billboard about the vertical axis, nearest filtering, alpha scissor 0.5 (a see-through picture, a quarter or more of whose drawn pixels are partly transparent, `Raster.IsTranslucent`, is blended by its alpha instead with `shaders/picture_billboard_translucent.gdshader`, which also plays its `animate()` looks: tg's water puffs, alpha 11 to 153, were cut away whole by the scissor, the space play test of 2026-10-15), **lit by the light grid like every other world surface** (`ALBEDO` for the shadowed Godot lights, `ALBEDO * anomaly_grid_light` in `EMISSION`; a standing picture reads the grid where it stands, a lying one at each fragment), no shadow. The `StandardMaterial3D` it replaced had no grid term, so a mob under a lit lamp was lit only by the few shadowed `Light3D` nodes, at the angle of a camera-facing normal: dark and shaded in a lit room while the walls, floors and props around it looked right (the owner's walk, 2026-10-09; shots before and after in the I1c results, `mobs-*.png`). The stand-in shapes (a capsule for a mob, a box for a thing with no picture) take the same term (`shaders/placeholder_lit.gdshader`); they were black in lit rooms, and `[anomaly] placeholders: ...` in the log names the types that are drawn as stand-ins (on the real server's Meta: 371 of 410 dynamic entities near the start, the 282 `/obj/machinery/camera` of all directions and the canisters, which the server sends with no picture). An appearance whose icon files are all there but whose states are missing from them (with no default state) is drawn as nothing, as BYOND draws it, not as a stand-in (`AppearanceCompositor.IsBlank`: tg's trail particles blank themselves with `icon_state = ""` after their `ion_fade` flick, effects_trail.dm:72; before the space play test of 2026-10-15 a jetpack's trail was a brown box in front of the eye for a second). **Particle effects** (`/obj/effect/particle_effect`: the ion trail, the water puffs, smoke) are never static props (`StaticPropRule`), so the entity layer plays their flicks and fades; one that appears within two tiles of the own mob's server tile is drawn from the drawn own body (moved by the own view's lag when it appears), and each fades out within a tile of the eye (`NearEyeFade`, DV46): a trail shows behind a flier, a spray leaves from just in front of the nozzle. 32 pixels are 2 m (6.25 cm per pixel), the icon square's centre on the entity's position and its bottom edge on the floor: tg's human (rows 3 to 31) is 1.81 m. The **frame** is chosen by the angle between the viewer and the mob's facing: with the compass bearing of the viewer from the mob minus the replicated `Yaw` (256 per turn, clockwise from north), the viewer in front sees the mob's south frame, behind it north, at its right east, at its left west (four 90 degree sectors; an icon with eight directions, found by `AppearanceCompositor.Directions`, uses eight 45 degree sectors: front-right is southeast). An entity without a capsule (`HasPos` false: items, tile movables) shows the frame of its own `Dir`. **Lying** (D104, `Posture`): tg's rotated sprite (the appearance's `transform` from `update_transform`) on a floor-aligned quad 2 cm above the floor, drawn the way BYOND draws the map seen from above: the picture's up is north, its right east, so a mob turned 90 degrees clockwise has its head to the east; its frame is its `Dir`. The own body is not drawn in first person (`hideOwn`).

**The turf kit.** `TurfKitPlan` groups the cells by kind and turf picture (the replica's `TurfAppearance`; a cell with none is grouped by its turf type and tinted as in M1), `MapRenderer` makes one multimesh per group: walls are boxes of 2 x 2 x 2 m (four sides and the top; D119, M2 had them 3 m high: the 32 x 32 picture covers a 2 x 2 m side once, `TurfKitPlan.WallVerticalRepeats` is the wall height over 2 m, 1), floors are 2 x 2 m tiles (the picture is a floor of 1 m tiles at 2 m per sprite), the ceiling is tg's `plating` darkened and repeated once per tile (a flat colour when the icons are missing). The pictures are the composed turf appearances cropped to their 32 x 32 square, with mipmaps and nearest filtering. Open space draws nothing. The M1 look (`Build(MapGrid)`: tinted boxes and a checkered floor) remains for a feed without appearances.

**Wiring for the game scene (M2 P8 or the integration).** `GameScene` keeps calling `_entities.Bind(feed)`, `_entities.Update(...)` and `_entities.TryGetPose(...)` as in M1; the layer reads `feed.Replica` itself (a version-1 feed throws `NotImplementedException`: placeholders). To get the pictures on the map call `_map.Build(_feed.Map, _feed.Replica, _entities.Textures)` instead of `_map.Build(_feed.Map)`. P8's pose source is `_entities.Poses = poseSource` (`IPoseSource`, asked once per entity per frame; without it the layer interpolates the replica's `Pos` samples itself). The HUD draws screen objects through `_entities.Textures.TryCompose(replica, appearance, dir, seconds, out ComposedAppearance)` (the private references included). **The pick interface** for the click ray: `_entities.TryPick(origin, direction, maxDistance, ignoreId, mobsOnly, out EntityPick)` returns the nearest entity (`EntityPick.EntityId`, the id of `ActionMessage.Target`) whose picture the ray hits on an opaque pixel (a lying mob: its quad on the floor), skipping the own mob; a wall nearer than the hit hides it (`MapRenderer.RayDistance`, found as the layer's sibling `Map`); an entity without a picture is picked by its box.

**Seeing it without a server.** `res://scripts/Render/Showcase.tscn` shows tg's real icons through the same `MapRenderer` and `EntityLayer` over a replica filled from `ShowcaseWorld` (a human as tg composes it: limb sprites tinted by the skin, eyes, hair, a GAGS jumpsuit, tg's damage overlays per zone, tg's lying transform; a toolbox; a test room with tg's floor and wall pictures). `ANOMALY_SHOWCASE=room|dirs|lying|damage|orbit`, `ANOMALY_SHOWCASE_CAM=x,y,eye,yawDeg,pitchDeg`, `ANOMALY_SHOWCASE_PICK=1` (rays at every entity and over their heads, printed), and the client's own `--screenshot-after=S,PATH`; `smoke.sh` runs the pick check headless and `SMOKE_SHOWCASE=DIR` renders the scenarios. The screenshots of M2 P7 (a human in each direction, lying, each damage level, the test room, one human seen from the four sides) are in `scratchpad/m2/p7-shots/` of the M2 work.

**Tests** (`tests/Anomaly.Server.Tests/Client/Render/`, `tests/Anomaly.Core.Tests/Tools/Icons/`): the tool on built files and on the real clone (all 1448 icons convert, the configs' icon files exist), the decoder against an encoder with every type, filter and interlace and against all real sheets, the blend modes against hand-computed pixels, sheets and animation timing, GAGS (hand-made configs and all real ones), the compositor (every rule above on 4 x 4 icons), the billboard math (frame by angle, rectangles, picks) and the turf plan. Tests that need the converted real icons use `godot/assets/tg` when it exists and otherwise run the built tool into a temporary folder; they are skipped when neither is possible (no clone).


### 2.10 The world renderer at MetaStation scale (M3 P6; D104, D113, D114, D116)

Status: M3 P6, 2026-10-08. The M2 turf kit (one MultiMesh per picture, one node per entity) cannot draw a 255 x 255 station: the scout measured 99 FPS with 1,769 separate billboard materials against 248 FPS with six draw calls (scope 2i). `MapRenderer` now draws the world in **chunks of 16 x 16 tiles** (256 on Meta, 107 non-empty), each with three MultiMeshes and an occluder; `EntityLayer` keeps the mobs and whatever moves.

**Per chunk (`MapRenderer`, `Render/`):**

| Node | What | Material |
|---|---|---|
| `Tiles<page>` | floors, ceilings and walls in **one** MultiMesh: one mesh holds a floor quad, a ceiling quad and a wall box 2 m wide and 2 m high (D119, `WorldGeometry.TileKit(WorldScale.WallHeight)`, built into the mesh by `WorldMeshes`), an instance draws one part (its `INSTANCE_CUSTOM.y`; the shader collapses the other parts' vertices to a point). tg's pictures are the layers of a **Texture2DArray** (`TileKit`: 32 x 32, mipmapped, nearest, 1,800 layers a page; a picture whose icon is missing is a flat tinted layer, M1's look). The ceiling is over **non-space cells only** (D116: space stays dark); F2 switches it off through a shader uniform | `shaders/turf_kit.gdshader` |
| `Props` | the static props (fixed-Y billboards) and the wall decals: one unit quad, one atlas | `shaders/prop_atlas.gdshader` |
| `Pieces` | the shaped things of D113 and the doors, one combined mesh with a part id per vertex (`PieceParts`) | the same shader |
| `Occluder` | an `OccluderInstance3D` of the chunk's wall boxes merged from runs (`OccluderPlanner`: 3,833 Meta walls become a few hundred boxes); `rendering/occlusion_culling/use_occlusion_culling` is on | - |

`CustomAabb` is the chunk's box, so the frustum culls whole chunks and a shadow pass draws only the chunks in a light's range.

**The prop atlas (`PropAtlas`, `Shared/World/AtlasBuilder`).** Every picture the props need is composed once by `AppearanceTextures` and packed into one 2048-wide atlas (shelves; it grows downward and an entry never moves), **trimmed to its drawn pixels** for billboards and decals, whole for the pieces. A metrics texture (RGBAF, two texels per picture) tells the shader the stored rectangle and the quad's size and offset in metres, so an instance carries only a picture id: `INSTANCE_CUSTOM` = (id % 2048, id / 2048, facing, frames), `COLOR` = (mode, part, flag, open fraction). A multi-direction icon stores 4 or 8 consecutive frames and the shader picks the frame from the angle between the camera and the prop's facing (`BillboardMath.ChooseDir`'s rule); the billboard turns about the vertical axis only (fixed Y). Meta: 389 pictures in 2048 x 512 pixels.

**The static-versus-moving rule** (`IStaticPropHost`, `StaticProps.cs`): an entity is a static prop, drawn in its chunk's batch, when it is not a mob, has no `Pos` and has received no X, Y or Z change since it spawned. `EntityLayer.Bind(feed, textures, host)` offers every entity to the host first; a claimed entity gets no node. On every new server tick `MapRenderer.Scan` looks for claimed entities whose cell changed (they leave the batch for good and become a node: `PropMoved`), whose appearance changed (the picture is replaced) and for doors. An entity whose picture cannot be composed (a missing icon) is not claimed and keeps M1's placeholder box. Static props are not pickable (the click pick is for mobs in M3; M4a's object clicks need a pick box per batch: open item). An entity with no appearance draws nothing.

**One sprite per face (the owner's rule, tested by `WorldGeometryTests`).** The meshes are data (`Shared/World/WorldGeometry`): every face maps its tg sprite **exactly once**, uv 0..1 over the whole face, no wrap or repeat (the Texture2DArray is sampled with `repeat_disable` and the uv clamped; the atlas lookup is clamped half a hair inside the stored rectangle, nearest filtering and no mipmaps, so no neighbouring picture or border pixel is read). A wall side shows its 32 x 32 sprite over 2 x 2 m (D119: a square face, square pixels; it is only stretched when the height setting is changed from 2 m), its top shows it once; floors and ceilings one sprite per 2 x 2 m tile. A part that is a share of a bigger picture has a reference rectangle: the airlock's two panels show the door sprite's left half (u 0..0.5) and right half (0.5..1) over the whole wall height, so together exactly one door, and the halves move with the panels; a full-tile window, a directional window, a pod door, a windoor and the flaps map x -1..1 and y 0..wall height (each flap strip its share), the railing x -1..1 and y 0..1.02; a table's top and every face of its top slab and legs show the whole table sprite, and decals and billboards show their drawn pixels once. The tg picture's v runs down, the mesh's up; u runs to the viewer's right on every face, so the back of a door is the mirror image a viewer from the other side expects.

**The height of the world (M3 R1, D119, amends D33).** Walls, doors, windows, grilles, pod doors, windoors, flaps and the ceiling are **2 m high, as high as a tile is wide**, so tg's square 32 x 32 sprite sits on a square 2 x 2 m face and is neither cut nor stretched. The standing eye is **1.2 m** (D120, the owner after the first walk of MetaStation; it was 1.6 m under D119; 0.5 m lying), which leaves the ceiling 0.8 m above it. The eye height is the other setting next to the wall's: `WorldScale.EyeHeight` (`DefaultEyeHeight` 1.2, accepted 0.8 to 1.9 m) is what `TileSpace.EyeHeight` and `CameraLayer.StandingEye` report, so the camera rig, the camera layer, the pick ray (from the camera's own position), `BenchRunner` and `LightRoomDemo` follow it; `--eye-height=M` or the options file's `eye_height` (`--option=eye_height=M`) set it once in `GameScene` before anything reads it (the `world:` line logs it), and the options panel has no slider for it either (the wall height is not there). The wall height is **one setting**, `WorldScale.WallHeight` (`Shared/WorldScale.cs`, engine-free; `DefaultWallHeight` 2, accepted 2 to 4 m), set once before the world is built from `--wall-height=M` or the options file's `wall_height` (`--option=wall_height=M`; GameScene logs it in the `world:` line) and not changed afterwards; the options panel has no slider for it because a different height needs a rebuilt world. Everything that depends on the height reads it:

| What | Derived from the setting |
|---|---|
| walls, the ceiling plane, full-height pieces (windows, directional windows, grilles, airlock panels, pod doors and shutters, windoors, plastic flaps) | `WorldGeometry.TileKit(height)` and `Pieces(height)`; the default overloads read `WorldScale.WallHeight`. The table's top is half the standing eye, 0.6 m (`WorldScale.TableTop`, M3 R5: below), and the railing keeps its own 1.02 m |
| the pod door's rise into the ceiling | the prop shader's `wall_height` uniform (set by `PropAtlas`): the slab rises by the wall plus 5 cm and is cut at the level's ceiling (M3 R5) |
| a table's top (and what stands on it) | `WorldScale.TableTop` = `TableShare` 0.5 of the standing eye: 0.75 m at the D137 eye of 1.5 m (0.6 m at the 1.2 m eye) (it was a fixed 0.9 m); `WorldGeometry.TableTop` and `TableTopUnder` (14 cm lower) read it when the pieces and the planner are built, so `--eye-height` moves the tables with it |
| a level's height and the floor of the level above | `TileSpace.LevelHeight` (= the wall height), hence `WorldY`, the chunk bounds, the occluder boxes, the light layer's level choice, the pick ray's level |
| wall mounts | shares of the wall: lamps 0.925 (1.85 m), signs 0.75 (1.5 m), panels 0.55 (1.1 m), cameras 0.85 (1.7 m), others 0.6 (1.2 m) (`WorldScale.*Share`, `PropKinds.MountHeight`); a decal is then fitted onto the face by its own height (`FitMount`); the light fixture's 14 cm box tops out at 1.92 m |
| the shadowed Godot lights | `WorldScale.LampHeight` (1.85 m) above the level's floor |
| `TurfKitPlan.WallVerticalRepeats` | wall height over 2 m per picture |

**The second walk (M3 R3, D121; the owner's findings on MetaStation after R2).**

- **Doors stand across their passage (`DoorAxis`).** The old rule looked at the closed turfs, windows and doors east-west and north-south of a door and fell back to NORTH, so a door between two dense hydroponics trays, or a row of firelocks across a hall (Meta has ten heavy ones in a column at x = 173) stood turned along the passage. The rule scores BOTH planes from the four neighbours (`CellClass`: *blocking* = a closed turf, a full-tile window, a grille, a door of tg's family or a firelock, a cell with a dense non-mob thing, which the replica's solidity bit says; *open* = a floor nothing dense stands on; space and the map's edge say nothing): a plane along x scores one for each blocking cell east and west and each open cell north and south, a plane along y the reverse, the higher wins (NORTH: the plane runs along x; EAST: along y). A tie goes to the face of a neighbouring door that is already decided (a door beside a door shares its axis: a double airlock, a row of firelocks in the open; the first of west, east, south, north), else to the same scores over the cells two and three further out, else NORTH, the old default. `ResolveAll` decides a whole map in a fixed order (z, y, x), whatever order the doors are listed in; a door that spawns later is placed against what the plan knows (`PlanIndex.DoorFaces`). Airlocks, pod doors, shutters and firelocks are covered; windoors and border-only firelocks keep their `dir` face. On Meta 77 of 1,205 doors changed (all NORTH to EAST: ten firelocks of the column, the shutter columns, seven airlocks); the doors between two walls are decided as before (a test checks all 752).
- **Windows, grilles and border pieces are joined in 3D (`Joints`, `BorderCorners`).** tg draws a wall run in the top-down view as one of 47 junction pictures; in first person the joint is geometry. A full-tile window or grille is a **centre post and an arm toward each neighbour it joins** (a closed turf, a full-tile window, a grille, a door frame: an airlock or pod door, not a firelock, which stands in a hall beside frames): a straight run is one continuous slab (the post and the east and west arms show the whole picture exactly once, 2 m by 2 m, as the old single slab did), a corner is an L, then a T and a cross; a window beside a wall closes the gap to it (the arm reaches the tile edge); the end of a run still spans its tile (a run that joins on one axis only keeps both arms of that axis); a window with no neighbour at all takes the axis the door rule gives it. The north arm is the east arm turned a quarter and the south arm the west arm turned, so the picture's lines run along the slab on both axes. The arms are computed in the planner from the neighbours (`Placed.Joints`, the BYOND direction bits N 1, S 2, E 4, W 8), not from tg's junction state, which the real server will put in the icon state (P4) and which nothing here depends on. The grille's arm is three bars 30 cm apart in a frame whose rails run to the tile edge. **Border pieces** (directional windows, railings, border firelocks; a windoor counts as a partner but gets no post) that meet at a tile corner, in one tile or in neighbouring ones, get a 12 cm corner post at that end (`BorderCorners`: a corner is named in doubled tile coordinates, a piece's low and high ends are its two corners, a post is drawn only where a piece of the OTHER axis ends too). All of it lives in the existing piece MultiMesh: the mesh's UV2.y names the arm or post a face belongs to (`GeoQuad.Arm`: 0 always drawn), the instance's `INSTANCE_CUSTOM.z` is the joints mask, and the shader collapses the faces whose bit is missing, so there is no new draw call (a window or grille is still one instance). Every instance of the piece MultiMesh runs the vertex shader for every vertex of the mesh, so the extra geometry is kept lean: the mesh is 175 quads instead of 149 (a grille's bars are crossed quads and its rails two quads, not boxes; the border pieces' corner posts are two parts of their own, `PieceParts.BorderPost` and `RailPost`, drawn as ONE extra instance only on the 409 border pieces of Meta that need a post, so the 890 pieces still pay nothing for them).
- **Border pieces take the picture of their full-tile counterpart (M3 R6, `BorderCounterparts`; the owner, fourth walk: the slime pens of xenobiology were low strips and had to look "tall and flat" like the full-tile windows).** tg draws a directional window, a windoor and a border firelock in the top-down view: a band of 4 to 7 pixels along one edge of the 32 x 32 square (a window's rows 25..31 for south, 0..6 for north, columns for east and west), the rest transparent. ### 2.12 Interaction (M4a P7; D124-D133, `docs/ai/specs/interaction.md`)

The client points, clicks, holds the radial, shows tg's hands, slots and open storages, and draws throws. **Nothing is predicted** (D38, D103): every click, hover and keybinding is an action the server runs through tg's own chain; the client only chooses the target, sends ids and shows what comes back.

**The pick** (`Shared/Play/WorldPicker.cs`, engine-free, tested in `tests/Anomaly.Server.Tests/Client/Interaction/`). One function, `IWorldPicker.Pick(PickRay, exclude, entitiesOnly)`, for the crosshair, the highlight, the hover, the radial and the click. The ray goes from the camera along the view through the cells (Amanatides and Woo over `IPickWorld`) to the first wall; the nearest of the following is the hit: a **billboard** (a mob or a moved item: `EntityLayer.CollectPickShapes`, the picture's opaque pixel, a lying one flat on the floor), a **static prop** of a chunk batch (`MapRenderer.CollectStatic` from its by-cell index: the prop's picture as a standing quad at its scale on its support, items at D121's half scale, a wall decal as a thin slab on its face; floor decals such as pipes and wires are not picked, the floor is), a **piece** (`PieceBoxes`: an airlock's closed slab or, open, its two ends; a pod door's slab; a firelock; a window's or grille's post and arms by their joints; a directional window, windoor or railing on its edge; a flap; a table as a box from the floor to its top, so a ray at its side is a click on the table and never on the floor under it), the **floor**, a **wall face** or the **ceiling** (the turf, with the face's tile-relative point). A wall hides everything behind it; `entitiesOnly` leaves the cells out as hits. The range is 8 m, and in throw mode 14 m (`PickThrow`: with no hit, the floor cell where the view meets the floor, or the cell at that range). `PickHit.IconX/IconY` are tg's `icon-x`/`icon-y`: for a picture the pixel under the ray counted from the atom's own 32 x 32 icon square (left is 1, bottom is 1, clamped to 1-32, `PickShape.Inside`); for a table top, a floor or a wall the tile-relative point times 32 rounded up. The reach mirror (`WorldPicker.InReach`: the own tile or a neighbour on the same level) colours the crosshair green or amber and never stops a click; the server decides reach (interaction.md 4.3). The crosshair shows its four ticks over any entity, and a translucent additive slab around the shape under it is the highlight (`HoverHighlight`; around the drawn pixels of a picture, the box of a piece, the floor or ceiling tile, or the whole wall cell; each is off by default and switched on in the options: `highlight_tile` for a floor or wall, `highlight_thing` for a thing, the owner 2026-10-09 and 2026-10-13); a click flashes the slab and puts a short ring on the crosshair (local feedback, the move waits for the server).

**Mouse and keys (D124, D53, D70).** Left is tg's left click and middle tg's middle click (`MiddleClickOn` swaps hands; with nothing under the crosshair it sends the swap-hands keybinding); the modifiers held at the click (Shift, Ctrl, Alt) go with it. A **right tap** (released within 0.25 s) is tg's right click on the target of the press; a **right hold** opens the radial. The keys are tg's: Q drop, E quick equip, X swap hands, Z activate in hand, R throw mode, Space hold throw mode (down and up), H and Delete stop pulling (protocol version 20; a pull is a Ctrl-left click), Tab cursor mode; Q and E fly the camera in the free mode, where the interaction keys are off. M2's `Help` and `Shove` bindings are now `PrimaryClick` and `SecondaryClick`: an option file with `bind.help=` or `bind.shove=` (or `--bind=help=KEY`) still reads (`KeyBindings.LegacyIds`), the file is written with `bind.primary_click` and `bind.secondary_click`, and a file written by M2 has no keys for the new actions, so tg's defaults stand. The scripted `--keys` clicks are taps (a release 60 ms after the press), so `click=right` is still the shove. `PlaySession.Click(ClickTarget, ...)` sends the version-4 action (target kind, id or turf, icon pixel); `Keybinding(code, up)` the keybinding; `Hover(target, now)` a hover when the thing under the crosshair changes, at most once per 0.1 s (the server's bucket lets ten a second through; the host runs one a tick). A hover is sent for an entity under the crosshair, and for a cell only in throw mode. Throw mode itself is read from the HUD (the `throw_catch` entry's `act_throw_on` icon state), since tg owns it.

**Hover and the radial (D125, D49).** The server's `ContextHints` (message 11, the Control channel; `IWorldFeed.ContextHintsReceived`, raised by `GameClient` and `FakeFeed`) answers a hover with tg's name for the thing and its labels for the held item. The screentip line under the crosshair shows the name and the left and right labels (the answer to an older hover is dropped: `HintsFor` matches the hovered target). `RadialModel` (a state machine over the press time and the mouse movement since it opened) builds the radial from tg's entries as sent, then the fixed ones: **Examine** (a Shift-left click), **Throw at** (throw mode on, then a left click), **Swap hand**, **Things here** (when the tile has more than one thing: a second, sticky list of the tile's items, left click chooses, anything else cancels; each item is a left click on it) and **Cancel**. The mouse is captured, so the aim is the movement since the radial opened, clamped; the release over an entry sends its click, in the centre does nothing. The highlighted entry has a thick frame and an arrow besides its colour, every entry is text (D70).

### 2.16 Fire and gas (M4b slice 3; D18, DV32)

**Burning air** (`Render/FireVolume.cs`). tg's hotspot (`/obj/effect/hotspot`) is an entity like any other; the entity layer draws it
as the tile's air on fire instead of its flat sprite (D334, DV433, `shaders/fire_volume.gdshader`): a box from the floor to the ceiling that reaches 0.35 m past its tile, cut by
the scene's depth and marched in eight steps through a rising 3D noise sampled on tg's pixel grid and stepped at 10 frames a second. The fire met along the ray adds its
glow (tg's `BLEND_ADD`) in eight bands of a palette from a dark red through the hotspot's light colour (tg's `update_color`) to a pale yellow, dimmed by tg's alpha; the glow
fades over the box's overlap, so burning neighbours add up to one even fire and its rim is ragged, and air within 1.2 m of the eye glows less so a fire around the eye
does not whiten the screen. Its stage (tg's icon state `light`, `medium`, `heavy`) sets how much of the air burns. Over open space it burns in the air, as the gas does.
A very hot fire's overlays (tg's `update_color`: `shieldsparkles` from 200,000 K, `overcharged` from 400,000 K, `fusion_gas` from 4,500,000 K) are read from the
hotspot's replicated overlays and drawn by `shaders/fire_extras.gdshader` as their pixels in the tile's air (DV433): 16 sparkles (five-pixel plus signs and dots), 16 level
dashes and 4 jagged bolts of 10 segments, placed at random points that change with each sprite's frame, the bolts only in `overcharged`'s bursts (its frames of
1, 1, 50, 1, 1, 1, 20, 1 and 40 ticks, the long ones empty); each pixel is its sprite's brightness times the hotspot's light colour, as tg's colour matrix makes it,
at the overlay's alpha. `ANOMALY_FAKE_FIRE_EXTRAS=sparkle,lightning,fusion` gives the fake map's fire those overlays.
The fire casts no shadow; the room's glow is the hotspot's replicated light (D24), one lamp for each three by three tiles and at most two shadows (DV242).
`ANOMALY_FAKE_FIRE=N` with `--fake-map` burns N by N tiles around the first spawn cell (`ANOMALY_FAKE_FIRE_AT=X,Y,Z` around that cell instead), for shots and frame
measurements. (Particle flames came first, then D302's flame planes standing on the floor, which read as a campfire and floated over open space.)

**Smoke and the blast** (`Render/SmokeVolume.cs`, `shaders/smoke_puff.gdshader`; `Render/BlastVolume.cs`, `shaders/blast_puff.gdshader`; D303, DV243). tg's smoke draws seven round camera-facing puffs per
tile on tg's pixel grid in hard grey bands multiplied by tg's colour, thinned by an ordered dither (tg's alpha and fade; tg's see-through kinds at 55%); with the eye in the tile a full-screen dither stands for being
in the cloud. What the smoke hides is the cell's opaque flag, as for a door. tg's explosion draws 26 puffs thrown out to three tiles over its second, from pale yellow to dark smoke.

**The gas haze** (`Render/GasLayer.cs`, `shaders/gas_fog.gdshader`). Every cell that shows gas (protocol 15.1) is a box of haze
from the floor to the ceiling, drawn by its back faces in one MultiMesh; the shader cuts the view ray by the box and by the
scene's depth and turns the length of gas into alpha (`1 - exp(-density * length)`), so neighbouring cells join without seams
and a camera inside the gas sees it. A gas's colour and how much of a tile it covers are the mean of tg's own sprite frames
(`icons/effects/atmospherics.dmi`: plasma, water vapour, ...); a cell's gases stack as tg's overlays do, each at its level's alpha,
and the stack's opacity is reached over 4 tiles of gas (DV32: tg's viewer looks down through one overlay, a first-person view
looks along the gas). A slow 3D noise moves through it; the light grid lights it; a change fades in a quarter of a second.

### 2.19 The airflow streams (D141, DV34)

`Render/AirflowLayer.cs`, `shaders/airflow_streams.gdshader`. The server sends the air flow of the cells around the player
(protocol 16: tg's pressure difference and direction of each SSair cycle); the layer draws it as thin streams of air into the
holes.

- **The field and the holes.** Each flow cell points at a neighbour (tg keeps one direction per turf: its strongest share
  of the cycle). The air leaves a cell through every space neighbour it has, and through the neighbour its direction names when
  that one has no flow: the wall square between the two cells (a breached wall: space with open floor on fewer than two sides),
  the floor square of the neighbour (a hole in the floor: space with open floor on two or more sides), or the cell's own floor
  or ceiling for a flow down or up. (Only the named neighbour counted at first: a cell beside a hole often points along it, so
  the owner saw no streams into the middle of three breached tiles, 2026-10-14.) A cell's exits, and exits whose cells touch
  (diagonals too), are one hole; every other flow cell belongs to the exits its chain of directions reaches first, and a stream
  takes one of them, the nearer the likelier. Where the air runs on into a cell that is not space and has no flow (a gas
  thinning out as it spreads, a vacuum filling), there is no hole: the streams run into that cell and fade (no red face). Rebuilt
  when an update arrives; living streams count for their hole again.
- **Vents and scrubbers** (protocol version 7). A floor device moving air is a source of its own, with its own budget (**Max
  per vent**, default 37) and its own scale (a working scrubber moves 1 to 5 kPa a cycle, a vent refilling a vacuum tens):
  out of the grate the streams are born on it, rise a little and spread over the floor in all directions (bent by the room's
  flow), slowing and fading within 0.8 to 2.2 tiles; into it they are born in the air around it (in the same room, open floor
  all the way), drawn to the point of the grate nearest to where they start, faster as they near it, and go down through the
  floor. Weak ones stay visible (a fifth of an opacity at least). The debug view rings a device with four arrows, green
  outward, blue inward.
- **The budget.** At most **Max streams** (default 880) live, at most **Max per hole** (126) on one hole. The holes within
  **Spawn distance** (20 tiles) of the camera whose area is in the camera's frustum share it in proportion to their strength
  (what a capped hole leaves goes to the others); a hole keeps a share of its budget by its strength (a draft under 30 kPa
  fewer, at least a fifth) and fills it over about a second. Nothing spawns for a hole out of view or far away, nor from a flow
  cell past the spawn distance; living streams finish their lives.
- **A stream.** Born at a random point of a flow cell of its hole (stronger cells more often), near the floor more often than
  near the ceiling; its path is traced once through the field (the four nearest cells' directions blended) toward the point of
  its hole's face nearest to where it starts (kept 0.12 tile off the face's edges, jittered by as much; a floor hole's point is
  drawn a little toward the middle), pulled harder toward it as it nears it, around corners by the cells' own directions, then
  on through the face and out, speeding up, for 0.9 to 1.5 tiles through a wall and 0.6 to 1 through a floor or a ceiling. A piece of the path (0.6 to 2.8 tiles, longer in a stronger
  flow) slides along it at 0.3 + 0.42 x sqrt(kPa) tiles a second (tg's push force grows with the square root of the difference).
  It lives 1.6 to 3 seconds: transparent when born, fading in over 0.45 s, semi-transparent in the middle of its life (more
  opaque and wider in a stronger flow), fading out over 0.6 s and when its head runs out of path; thinner and fainter at both
  ends of the piece.
- **Drawing.** One mesh rebuilt every frame: each stream a camera-facing ribbon of 12 segments (vertex colour and alpha, a soft
  edge across), unshaded, no depth write, lit by the light grid with a little glow of its own, darker over a light background
  (it reads the screen behind it: a white haze over space, a grey streak over the near-white floors, where white was not seen).
  Its colour is white, or, when the cell it starts in shows a gas haze (2.16), the haze's colour made more vivid (purple in
  plasma). The culling box is the ribbons' own each frame. (The first build's taper made the last vertex of every ribbon NaN,
  sin(pi) being a hair below 0, so the mesh's box was a point at the origin and the streams vanished whenever the origin was out
  of view, 2026-10-14.)
- **Debug.** Solid flat arrows on each flow cell, drawn over everything (bigger in a stronger flow; teal, amber where the
  difference is above 16.7 kPa, tg's push threshold for a human: pressure_resistance 25), diamonds where the air goes through a
  floor or a ceiling, and the holes' faces as see-through red squares. (The first arrows were 1-pixel lines under the floor's
  surface that the owner could not see, 2026-10-14.) `ANOMALY_AIRFLOW=0` starts with the streams off, `ANOMALY_AIRFLOW_DEBUG=1` with
  the arrows on, over the saved settings.
- **Settings.** Saved in the options file with the dev menu's others (2.17: `dev.airflow`, `dev.airflow_max_streams`,
  `dev.airflow_max_per_hole`, `dev.airflow_max_per_vent`, `dev.airflow_spawn_distance`, `dev.airflow_debug`).

Checked on the real server (2026-10-14, `--room 24 --airflow-radius 40`, `--view` free camera, `breach 4 16`): the streams curve
across the floor into the breach and out into space, a second hole shares the budget, a drained room keeps faint drafts, and in a
plasma room the streams are purple.

### 2.20 Sound playback (M4b audio slice 3; DV36 to DV39)

`Audio/SoundPlayer.cs` (a node under the game scene), `Audio/SoundLibrary.cs`, the engine-free `Shared/Audio/SoundMixer.cs` and
`Shared/Audio/SoundIndex.cs`; the rules and the numbers are protocol.md 22.3.

- **What plays.** The server's sound events (protocol 13) through the mixer onto 32 positional and 8 centred voices. tg's volume is
  the whole attenuation: the 3D players have no attenuation model, distance limit, distance filter or doppler; they only pan, from
  the current Camera3D (the first-person view is the listener, DV36). A positional sound sits at its tile's centre at ear height.
- **Muffle and occlusion.** Two buses made in code under Master: `Sfx` and `SfxMuffled` (a low-pass filter). A voice whose
  max(muffle, occlusion) reaches the threshold (0.5) goes through the muffled one; the occlusion also lowers the volume by
  (1 - k x occlusion), k 0.65. Two buses and a threshold rather than a cutoff per voice: Godot's filters are bus effects, a bus per
  voice would be 40 buses, and the owner's listening test decides the numbers first; graded buses (two or three cutoffs) are the
  next step if the threshold sounds too abrupt. The environment (reverb) is not used yet (the owner: after a listening test).
- **Files.** The sound tool's copies under the asset root (`godot/assets/tg`, or `ANOMALY_SOUND_ROOT`), read at run time where the
  index's `file` says (`sound/` or `sound-nc/`, D35), cached about 64 MB; a missing file is logged once and plays nothing.
- **The fake server.** `--fake-server` plays tg's airlock sound 3 tiles east of the player every 2 s (`FakeServerOptions.DoorSounds`).
- **Smoke.** At the quit the client prints `[anomaly] audio: events N voices M missing K (active, stolen, expired, files, driver)`;
  godot/tools/smoke.sh wants events and voices above 0 and missing 0 in the fake-server run when the sound index exists. Godot's
  headless run uses the Dummy audio driver: nothing is heard, the line checks the bookkeeping.
- **Settings.** The dev menu's Audio tab (2.17), saved as `dev.audio_*` lines.
